## 0. 요약 (핵심 발견 5)

1. **[구조적 취약, 손실 아님] 흡수된 사진은 `_temp/` Storage 경로에 영구 종속.** 메인앱이 temp를 흡수할 때 blob이 아니라 snap이 이미 올린 URL(`replacements/_temp/{day}/{seq}/...`)을 그대로 replacement 레코드에 복사(`replacement-modal.js:1215/1248`)한다. 저장 시 temp **RTDB** 노드만 삭제(`:1388`)되고 **Storage blob은 영구 잔존**(정리 스크립트·lifecycle 전무, MEMORY "Storage 자동삭제 금지"와 정합). → 지금은 사진이 보이지만 (a) `_temp/`가 무한 누적, (b) 영속 레코드가 "temp"라는 이름의 경로에 영구 결합.
2. **[진짜 손실 가능] 당일(KST) 미흡수 temp는 이튿날 사실상 사라짐.** `tempPhotos/{day}` 오래된 날짜 노드를 정리하는 코드는 없으나, 흡수(`prefillTempForSeq`)는 **오늘 날짜만** 조회(`:496`). 당일 흡수 안 된 snap 사진은 다음날 어떤 워크플로우에도 안 잡힘. 유일한 복구단서 `saveLog`도 이틀 뒤 prune(`snap.html:443`, `replacement-modal.js:1368`)이라 **복구창=2일**.
3. **[매칭 실패 근본원인] 두 앱의 작업번호 계산이 불일치.** snap `nextEmptySeq`는 temp 점유번호까지 셈(`snap.html:529,536`). 메인앱 `usedSeqsToday`는 `replacement_list`의 daily_seq만 셈, **temp 점유는 무시**(`replacement-modal.js:439`). → 메인앱 자동 seq와 snap seq가 어긋나면, 공통 케이스(운영자 자동번호 == snap 번호)에서 흡수 confirm이 뜨지 않고 조용히 스킵.
4. **[부분 손실] 저장 시 temp 노드 통째 삭제 → 미흡수 필드 파기.** 흡수는 빈 칸만 채우는데(`:513-525`), 저장 성공 시 `_pendingTempPath` 전체 노드를 remove(`:1388`). 이미 채워져 있거나 `canX=false`라 흡수 안 된 temp 필드(추가 철거사진·검침값 등)는 함께 삭제됨.
5. **[기존 이슈는 코드상 해결됨]** ifEmpty 오판(폴백 SDK 경로엔 잔존, 워커경로는 제거 `:853`), Blob→File(`snap.html:783`), loadToday 원자화(`:506`), temp blob 고유토큰(`:808`), jobId 랜덤접미사(`:741`) — 전부 인코드 수정 완료. 열린 항목은 위 1~4.

## 1. 연동 구조 (저장 경로 · 흡수 로직)

### 1.1 snap이 찍은 사진 저장 (snap.html `autoSave` :799~934)

작업번호 s의 계기 할당 여부(`hit = seqIndex[s]`)로 두 시나리오:

- **A. 계기 할당됨(hit 있음)** — 사진을 그 계기에 직접.
  - Storage: `replacements/{hit.addr}/{hit.meterId}_{Date.now()}/{slot}.jpg` (`:810`)
  - RTDB: `workStatus/{RG}/{addr}/replacement_list/{meterId}` 하위
    - 철거 LCD(`rv_{fid}`) → `removal_photos[fid]`, 대표칸이면 `old_meter_photo`도 (`:855-861`)
    - `old` → `old_meter_photo`, 그 외 → `new_meter_photo` (`:862-869`)
- **B. 미할당(hit 없음)** — 임시보관함.
  - Storage: `replacements/_temp/{day}/{s}/{slot}_{uniq}.jpg` — `_uniq`로 blob 덮어쓰기 차단(`:808-811`)
  - RTDB: `tempPhotos/{RG}/{day}/{s}` 하위 (`removal_photos[fid]` / `removal_photo` / `new_meter_photo` + `daily_seq`/`worker`/`updated_at` 메타) (`:873-886`, 폴백 `:916-931`)

두 경로 다 별도로 `saveLog/{RG}/{day}`에 append-only 이력 push(`:815-827`) — RTDB가 덮여도 Storage path 추적 복구용. 단 이틀 뒤 prune.

경로 선택은 `autoSave` 진입 즉시 `await loadToday()`로 최신 할당 재조회(`:802`) — snap이 사진 올리기 직전 종로맵에서 그 계기가 방금 할당됐으면 A로 붙게 하는 staleness 픽스.

업로드 실행: 네이티브 `AndroidUpload`(WorkManager 백그라운드, 자동재시도) 우선, 없으면 `restUpload`(REST, File로 감싸 Capacitor 손상 회피) 폴백(`:830-933`). 업로드 손상(2바이트 `{}`) fail-loud 검증(`:789-791`).

### 1.2 메인앱 흡수 (replacement-modal.js `prefillTempForSeq` :489~577)

- 트리거: `setDailySeq(n)` 끝에서 항상 호출(`:465`). `setDailySeq`는 신규(`loadDailySeq→:604`)·수정(`:279`)·+/- step(`:585,589,604`) 모두에서 불림 → **모달 열 때도 자동 발화**(운영자 수동 step 불필요, 이 부분은 양호).
- 조회: `tempPhotos/jongno/{today}/{seq}` **오늘 날짜만**(`:496`).
- 판정: 빈 칸(사진/검침값/계기번호/제조/LCD영역)만 채울 수 있는지(`canX`) 계산(`:518-525`). 채울 것 없으면 return.
- 확정: 작업번호별 첫 진입 시 `confirm`으로 사람이 "이 계기로 불러올까요?" 승인(`:535-540`). 자동 흡수 금지(snap 번호가 다른 계기일 수 있어 사람 확정 강제 — 영준님 지시 `:470`).
- 채움: **빈 칸만** `keepRemovalPhotoUrls[fid]`/`keepNewPhotoUrl`/입력칸에 temp URL·값 복사(`:544-573`). `_pendingTempPath` 저장(`:574`).
- 저장(`saveReplacement`): 흡수분은 blob이 없어 `Promise.resolve({ url: keepUrl })`로 그대로 결과에 실림(`:1215,1248`) → **재업로드 없이 temp URL을 영속 레코드에 기록.** 저장 성공 후 `_pendingTempPath` 노드 remove(`:1388`).

## 2. 누락 시나리오 (코드 근거)

### S1. `_temp/` Storage blob 영구 잔존 + 영속 레코드의 temp 경로 종속 [취약]
- 조건: 항상(흡수가 일어나는 모든 건).
- 근거: `replacement-modal.js:1215/1248`가 흡수 URL을 재업로드 없이 레코드에 복사, `:1388`은 RTDB만 삭제. `grep _temp/tempPhotos` 결과 Storage blob 정리 코드·lifecycle 전무.
- 영향: 계기 레코드 `removal_photos[fid]`가 `replacements/_temp/...` 경로를 영구 참조. `_temp/` 무한 누적(비용·정리 불가). 향후 누가 `_temp/`를 지우면 **정상 완료 계기의 사진이 죽음**.

### S2. 당일 미흡수 temp의 이튿날 실질 손실 [손실]
- 조건: snap이 사진 올렸으나 그날 종로맵에서 해당 계기 흡수 미실행(작업자가 종로맵 저장을 안 함/다음날 함, confirm에서 '아니오' 후 미복구 등).
- 근거: 흡수는 `today`만 조회(`:496`), `tempPhotos/{옛날짜}` 정리 코드 없음(고아 데이터로 방치되나 UI 진입점 없음). `saveLog` 복구도 2일 창(`snap.html:443`).
- 영향: 사진·검침값이 존재하나(Storage/RTDB에는 남음) 어떤 화면에서도 계기에 연결 불가. 복구=수동 RTDB 조회.

### S3. seq 계산 불일치로 흡수 confirm 미발화 [손실·매칭실패]
- 조건: snap과 메인앱이 같은 작업 건에 서로 다른 자동번호를 부여 → 운영자가 연 seq에 temp가 없어 confirm이 안 뜸.
- 근거: snap `nextEmptySeq`는 temp 점유 포함(`snap.html:529`), 메인앱 `usedSeqsToday`는 `replacement_list`만(`:439`). temp만 있고 아직 미할당인 번호를 메인앱은 "빈 자리"로 보고 그 번호에 새 계기를 배정 → snap이 **다른** 번호로 올린 사진과 어긋남. 반대로 snap이 temp로 점유한 번호를 메인앱이 다시 auto-pick해 충돌.
- 영향: 사진 미흡수(운영자가 수동으로 seq를 snap 번호에 맞춰 step해야만 흡수됨).

### S4. 저장 시 temp 노드 통째 삭제로 미흡수 필드 파기 [부분손실]
- 조건: temp에 여러 필드가 있는데 일부만 흡수(나머지 칸이 이미 차 있거나 `canX=false`).
- 근거: 흡수는 빈 칸만(`:513-525`), 저장 성공 시 `_pendingTempPath` **전체** remove(`:1388`).
- 영향: 흡수 안 된 temp 필드(추가 철거사진/야간·무효·최대 검침값 등)가 함께 삭제. Storage blob은 남지만(saveLog 2일) 연결 끊김.

### S5. confirm '아니오' 후 영구 미제안 [운영손실]
- 조건: 운영자가 confirm에서 '아니오'(`_tempDecisions[seq]='no'` `:494`) 후 마음 바꿔도 그 모달 세션 내내 재제안 없음. 모달 닫으면 `_tempDecisions` 리셋(`:105`)되나, 그 사이 저장해버리면 temp는 남되 흡수 기회 상실 가능.
- 영향: 경미(모달 재오픈 시 다시 제안). 단 S2와 겹치면 손실.

### (참고) 이미 해결된 것
- 동시 업로드 temp 유출 race → loadToday 원자 교체(`:506-531`) + autoSave 진입 재조회(`:802`).
- ifEmpty 오판 → 워커 경로에서 제거(`:853`, "무조건 저장"). **단 restUpload 폴백 경로(웹/구앱)엔 `setIfEmpty` 잔존**(`:908-914`) → 종로맵이 먼저 넣은 값 있으면 snap이 스킵. 폴백 사용 시 재발 소지.
- Blob→File 손상 → File 래핑 + size 검증(`snap.html:783,789`).
- daily_seq 중복 착시 → temp blob `_uniq` 토큰(`:808`), jobId 랜덤접미사(`:741`).

## 3. 해결책

| # | 문제 | 해결책 |
|---|---|---|
| S1 | temp blob 영구 종속·누적 | 흡수 저장 시 keepUrl이 `_temp/` 경로면 **blob을 영속 경로로 재업로드(server copy)** 후 레코드엔 새 URL 기록. 그러면 `_temp/` 를 안전하게 주기 prune 가능. (지금은 재업로드 없이 URL만 복사 `:1215`) |
| S2 | 당일 미흡수 손실 | (a) `prefillTempForSeq`가 today뿐 아니라 **어제까지** 조회하거나, (b) 미흡수 temp를 목록화하는 "보관함" UI 추가. 최소한 `tempPhotos/{옛날짜}`를 saveLog처럼 N일 보관 후 정리(현재 무한 방치). |
| S3 | seq 계산 불일치 | 메인앱 `usedSeqsToday`가 **`tempPhotos/{today}` 점유번호도 포함**하도록 확장(snap `nextEmptySeq`와 동일 기준). 최소한 loadDailySeq가 temp 점유를 회피하게. |
| S4 | 저장 시 미흡수 필드 파기 | 저장 후 temp 노드를 통째 remove하지 말고, **흡수한 필드만 delete**(부분 삭제). 남은 필드는 다음 계기가 흡수하도록 보존. |
| 폴백 ifEmpty | restUpload 폴백에 setIfEmpty 잔존 | 폴백 경로도 워커 경로와 동일하게 "무조건 저장"으로 통일(작업자 사진 우선). |
| 공통 | 검증 체크 | 마감 후 배치: `saveLog`(src=snap)와 `replacement_list`를 대조해 **흡수 안 된 snap 사진 리스트업**(2일 창 내). 이미 존재하는 saveLog를 소비하는 리컨실 스크립트 1개면 S2/S4 손실을 조기 탐지·복구 가능. |
