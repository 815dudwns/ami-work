# 종로맵(계기맵) 웹 환경 사진 촬영→업로드 누락 분석

작성: 2026-07-03 · 대상: `jongno-combined` 종로맵(웹앱) · 비교대상: 보조앱 snap.html(네이티브 WorkManager)

> 배경: 보조앱(snap.html)은 네이티브 WorkManager로 백그라운드 업로드 + 실패 5회 재시도 + 실패 시 갤러리 저장이라
> 사진 백업이 튼튼함. 반면 종로맵은 순수 웹앱이라 사진 촬영본이 **브라우저 메모리에만** 존재 → 누락 우려.
> 코드 실측 근거로 실제 위험 시나리오와 web에서 현실적인 해결책을 정리.

---

## 1. 사진 촬영/선택 → 업로드 → workStatus 기록 전체 경로

관련 파일: `js/replacement-modal.js`(입력 모달·저장), `js/photo-uploader.js`(압축·Storage 업로드), `js/firebase.js`(RTDB), Firebase JS SDK **9.22.0 compat**(map.html).

### (1) 촬영/선택 → 메모리 blob 보관
- `onPhotoSelect(slotId, file)` — `js/replacement-modal.js:624`
  - `file.arrayBuffer()`로 메모리 Blob으로 1회 materialize(삼성 content:// 다중 디코드 회피) — `:630-631`
  - 압축: `PhotoUploader.compress(mem)` — `:640` → 미리보기 `setPhoto()` — `:641`
  - `setPhoto(slotId, blob)` — `:366` — 압축본 blob을 **모듈 변수**에 보관:
    - 지침칸: `removalPhotoBlobs[field] = blob` — `:375`
    - 신계기: `newPhotoBlob = blob` — `:378`
    - 원본(고화질 LCD 크롭용): `removalPhotoOriginals[field] = mem` — `:637`
  - YOLO로 LCD 영역 자동검출 → `removalPhotoRegions[field]` — `:649-656`

### (2) 저장 버튼 → 업로드 → RTDB set (핵심: `onSave`, `:1076`)
- 검증/폴백: 필수값(사진·검침값·계기번호·제조년월) 누락 시 완료 대신 draft로 폴백 — `:1175-1195`
- 업로드 태그 배열 구성 — `:1202-1267`
  - 칸별 철거 사진: `PhotoUploader.compressAndUpload(blob, `${baseDir}/${fid}.jpg`)` — `:1214`
  - LCD 고화질 크롭본(best-effort, try/catch 무시) — `:1221-1237`
  - 신계기 사진: `:1247`
  - stats 썸네일 old/new(best-effort, .catch 무시) — `:1254-1267`
  - `baseDir = replacements/{addrKey}/{oldMeterId}_{ts}` — `:1199`
- **일괄 실행**: `const results = await Promise.all(uploadTasks.map(t => t.promise))` — `:1269`
- 업로드 실패는 여기서 **throw** → `onSave`의 `catch`로 감(썸네일/LCD 크롭만 개별 .catch로 무시)
- URL 매핑 → `replacement` 객체 구성(removal_photos·new_meter_photo 등) — `:1272-1353`
- **RTDB 기록**: `statusRef.child(addrKey).child('replacement_list').child(oldMeterId).set(replacement)` — `:1364-1365`
- 성공 후: `saveLog/jongno/{날짜}.push(...)`(append-only 이력) — `:1369-1385`
- 성공 후: `_committed=true` → `setTimeout(close, 800)` — `:1401-1402`

### (3) Storage 업로드 실체 (`PhotoUploader`, `photo-uploader.js`)
- `compress()` — 800px/q0.40 + ICC 제거 — `:8-42`, `stripICC` `:45-65`
- `upload(blob, path)` — `firebase.storage().ref(path).put(blob).getDownloadURL()` — `:68-76`
- **재시도 설정 없음** = Firebase SDK **기본값 사용**: 업로드(`put`) `maxUploadRetryTime` 기본 600,000ms(10분), 연산(`getDownloadURL`) `maxOperationRetryTime` 기본 120,000ms(2분). 즉 **세션이 살아있는 동안** 일시적 네트워크 실패는 SDK가 자동 재시도함. 문제는 이 재시도가 **세션(WebView)이 살아있을 때만** 유효하다는 점(아래 2절).

### (4) workStatus 오프라인 큐 — 사진 저장에는 미적용 (중요)
- `firebase.js`의 오프라인 이벤트 큐(localStorage `EVENTS_KEY`)는 `type: 'state'|'reset'|'check'|'uncheck'`만 담음 — `js/firebase.js:80-122`
- 즉 **마커색(상태)·체크박스만** 오프라인 큐로 보호됨. **교체기록(replacement_list) + 사진은 큐를 안 탐** — `onSave`가 `node.set`을 직접 호출(`:1365`).
- `saveLog`(`:1369`)는 저장 **성공 후** 실행되는 append-only 이력 → 이후 동시저장/번호중복으로 replacement_list가 덮여도 복구용. **업로드/set 실패 시엔 아무것도 안 함**(백업 아님).

## 2. 웹 환경 사진 누락 시나리오 (코드 근거 + 실제 발생 가능성)

### A. WebView 백그라운드/킬/새로고침으로 메모리 blob 증발 — **실질 최대 위험**
- 촬영본 blob은 전부 모듈 변수(`removalPhotoBlobs`/`newPhotoBlob`/`removalPhotoOriginals`)이며 **IndexedDB/localStorage에 절대 안 써짐**. `open()`이 매번 `{}`/`null`로 리셋 — `js/replacement-modal.js:98-101`.
- 따라서 **저장 버튼을 누르기 전** 또는 **`Promise.all`(`:1269`) 업로드 중** WebView가 백그라운드로 프리즈/OS 킬되거나, 페이지가 새로고침/이탈되면 → 촬영본 **전량 소실**. 재입력밖에 답 없음.
- 모바일 WebView는 화면 OFF·타 앱 전환 시 JS·네트워크가 freeze되는 특성이 있어(아미큐/계기큐 사례로 이미 확인된 패턴), 업로드 burst 도중 프리즈 가능성이 현실적임.
- 뒤로가기는 가드됨(`_installBackGuard`, `:346`) — 안드 뒤로가기로 인한 소실은 방어됨. 하지만 OS 킬/새로고침/홈버튼 후 장시간 방치 후 복귀는 방어 못 함.

### B. 부분 업로드 = Storage O · RTDB X (비원자성) — **데이터 정합성 위험**
- 순서: 사진 업로드(Storage) 완료 → 그 URL로 `replacement` 구성 → `node.set()`(RTDB) — `:1269 → :1365`.
- 업로드는 성공했는데 `set` 직전/중 실패(네트워크 끊김·세션 킬)하면 → **Storage에 사진 객체는 남고, RTDB엔 기록 없음** = 고아 사진 + 작업 미기록. 사용자 화면엔 "저장 실패" 토스트만.
- 반대(RTDB만 O·Storage X)는 구조상 안 남음(URL이 있어야 set하므로). 대신 썸네일/LCD 크롭본은 개별 .catch로 무시되므로 "본 사진 O·썸네일 X"는 정상 허용(stats가 원본 폴백).

### C. 단발 업로드 실패 = 즉시 소실은 아님(재시도 가능) — 위험 **낮음**
- `onSave` `finally`(`:1410-1416`): 실패 시 `_committed`가 false라 **모달 유지 + 폼 재활성 + blob 미삭제**. 즉 사용자가 보는 앞에서 **다시 저장** 누르면 됨.
- SDK 기본 재시도(10분)까지 겹쳐 일시적 네트워크 실패는 대체로 자체 회복. **진짜 소실 구간은 A(백그라운드/킬/이탈)** 로 좁혀짐 — "실패=즉시 소실"은 과장.

### D. localStorage quota(iOS 5MB) — 사진 저장은 **안 막음** (구별 필요)
- 아미맵 사고는 상태쓰기가 localStorage 큐를 **경유**해서 quota throw가 DB 쓰기를 막았던 것.
- 종로맵 사진/교체 저장은 **직접 `node.set`**(큐 미경유, `:1365`)이라 **quota와 무관하게 저장됨**.
- 다만 quota는 workStatus 미러(`localStorage.setItem`, `firebase.js:543`)·상태/체크 이벤트 큐를 깨뜨릴 수 있음 → **마커색/체크박스 동기화**엔 영향. 사진 자체엔 영향 없음.

### E. Blob 손상 — 위험 **낮음** (snap과 메커니즘 다름)
- snap의 2바이트 `{}` 사고는 Capacitor `restUpload`가 Blob을 잘못 직렬화한 네이티브 버그.
- 종로맵은 브라우저 JS SDK `ref.put(blob)`로 Blob을 네이티브 지원 → 동일 손상은 발생 안 함. `compress()`가 canvas→Blob으로 새로 생성하므로 원본 파싱 실패도 회피(실패 시 원본 폴백, `:642-645`).

### F. 동시 업로드 race — 종로맵 메인은 위험 **낮음**
- 한 모달 저장은 태그 배열을 `Promise.all`로 한 번에 처리(인덱스 의존 제거, 태그 매핑) — 칸 섞임 없음.
- snap의 temp 유출 race는 보조앱 전용(daily_seq 전역리셋)이라 종로맵 메인엔 해당 없음. 저장 버튼 자체도 `saveBtn.disabled`(`:1085`) + `_committed` 잠금으로 이중 제출 차단.

### G. 업로드 완료 확인 없이 모달 닫힘 — 구조상 **방어됨**
- `close`는 `await`(업로드+set) 성공 후 `_committed=true` 다음에만 `setTimeout(close)` — `:1401-1402`. 실패 시 모달 안 닫힘. "확인 없이 닫힘"은 정상 경로에선 발생 안 함(단, A의 OS 킬은 close 여부와 무관하게 소실).

## 3. 보조앱(네이티브 WorkManager) 대비 웹의 백업 취약점 + 해결책

| 항목 | 보조앱 snap(네이티브) | 종로맵 웹 | 격차 |
|---|---|---|---|
| 촬영본 영속성 | (JS압축본) 워커 enqueue 후 네이티브가 보관 | **메모리 모듈변수만**(`:98-101`) | 큼 |
| 백그라운드 업로드 | WorkManager가 앱 죽어도 계속 | WebView freeze/kill 시 **중단** | 큼 |
| 재시도 | 워커 5회 재시도 | SDK 기본 10분(세션 살아있을 때만) | 중 |
| 최종 실패 폴백 | **갤러리 저장** | 없음(토스트만) | 큼 |
| 정합성 | 워커가 Storage+RTDB 순차 보장 | 비원자(B: Storage O·RTDB X 가능) | 중 |

### 웹에서 현실적인 해결책 (우선순위)

1. **IndexedDB 대기 blob 큐(pending upload queue) — 핵심**
   - 저장 버튼 시 업로드 **전에** 촬영 blob들 + 메타(addrKey·oldMeterId·검침값·ts)를 IndexedDB에 먼저 기록(`idb.js` 래퍼 확장, IDB는 blob 저장 가능·용량 큼).
   - 업로드+set 전 과정 성공 시에만 해당 IDB 엔트리 삭제.
   - 앱 시작 시 대기 큐 스캔 → 미완료분 자동 재업로드(드레인). A(킬/이탈)·B(부분업로드)를 동시에 해결. **가장 효과 큼.**

2. **원자적 커밋 순서 재정비(부분 업로드 방지)**
   - 업로드 성공 URL을 IDB 큐 엔트리에 갱신 → `node.set` 성공까지 큐 유지. set 실패해도 재시도 시 이미 올라간 Storage URL 재사용(중복 업로드 회피). 고아 사진 최소화.

3. **업로드 완료 게이트 강화(현재도 있음) + 실패 시 명시 UX**
   - 현재 `_committed` 게이트는 양호. 추가로 실패 토스트를 "다시 저장" 버튼/자동 재시도 배지로 승격해 사용자가 소실로 오인하지 않게.

4. **Service Worker Background Sync(보조)**
   - Chrome/안드로이드에서 WebView 백그라운드에도 업로드 재개 가능. **단 iOS Safari 미지원** → 종로 작업자 폰이 안드 위주면 유효, iOS는 IDB 큐(1번)에 의존.

5. **완료 검증(주기 감사)**
   - `saveLog/jongno`(이미 존재)와 실제 Storage 객체·replacement_list를 대조하는 서버측 감사 스크립트로 "Storage 있는데 기록 없음/기록 있는데 URL 깨짐"을 사후 탐지. 근본 방지는 아니나 유실을 놓치지 않는 안전망.

## 핵심 요약 (취약점·해결책 5)

1. **[최대] 촬영본이 메모리(모듈변수)에만 존재** — IDB/localStorage 미영속(`replacement-modal.js:98-101,366-381`). WebView 백그라운드 freeze/OS 킬/새로고침/이탈 시 전량 소실. → **해결: IndexedDB 대기 blob 큐(저장 전 기록 → 성공 시 삭제 → 앱 시작 시 드레인).**
2. **[정합성] 비원자 커밋** — Storage 업로드(`:1269`) 후 RTDB set(`:1365`) 사이 실패 시 고아 사진 + 기록 누락. → **해결: 큐 엔트리에 업로드 URL 저장 후 set 성공까지 유지(재시도 시 재사용).**
3. **[구별] 오프라인 큐는 상태/체크만 보호, 사진 저장은 직접 set** — `firebase.js:80-122`. 따라서 iOS localStorage quota는 **사진 저장을 막지 않음**(마커/체크 동기화만 영향). snap의 Blob `{}` 손상도 웹 JS SDK엔 미발생. → 위험 재분류(과대평가 방지).
4. **[완화됨] 단발 실패는 즉시 소실 아님** — `finally`가 모달 유지 + blob 보존 + 폼 재활성(`:1410-1416`), SDK 기본 10분 재시도. 진짜 소실 구간은 백그라운드/킬로 좁혀짐. → **해결: 실패 UX를 "다시 저장/자동 재시도"로 명확화.**
5. **[플랫폼] Service Worker Background Sync는 안드로이드만** — iOS Safari 미지원. → **해결: 안드=Background Sync 병행 가능, iOS=IndexedDB 큐가 유일한 현실 방안.** (근본책은 결국 1번.)
