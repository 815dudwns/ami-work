# 아미큐 OCR 실패 표본 자동수집 — 통신팀 설계 (2026-07-27)

PM 지시(pm-ocr-sample-collect-20260727.md) 응답. **구현 전 — 계약 확정 대기.**

## 결론 요약

- **폰(APK) 수정 불필요.** 매칭방식 (a) 채택 확정 — 실측으로 검증함.
- 백엔드(`cst-input/backend/app.py`) `/api/ocr` + `/api/saveact` 두 지점만 건드리면 끝난다.

## 매칭방식 (a) 채택 근거 — 실측

### 코드 사실관계
- `CollectViewModel.masterNext()`(L188~199): `masterPhotos.value["5"]`(계기판 사진, base64) 원본을 그대로
  `Backend.ocr()` → `/api/ocr`에 보낸다.
- `CollectViewModel.uploadQueueItem()`(L336~357): saveAct 전송 시 **같은 슬롯 "5"의 b64**를
  `ImageProc.stampExifTime(ctx, b64, t)`로 감싸서 보낸다. 슬레이브도 동일(`s.photo5` → OCR, 나중에
  `stampExifTime`으로 감싸 slot "5"에 담아 전송).
- `ImageProc.stampExifTime()`(ImageProc.kt:60~74)은 `androidx.exifinterface.ExifInterface`로
  `TAG_DATETIME*` 3개만 `setAttribute()` + `saveAttributes()` — **JPEG의 EXIF(APP1) 세그먼트만
  덮어쓰는 논-디스트럭티브 편집**이다. 압축 이미지 데이터(SOS 세그먼트/픽셀)는 건드리지 않는다.

### 실측 (피직스 시뮬레이션 — Android ExifInterface와 동일 부류의 in-place APP1 편집)
`piexif.insert()`(Python, 같은 종류의 비파괴 EXIF 삽입)로 검증:
```
원본 파일크기 1149 / 스탬프후 파일크기 1187   (파일바이트는 다름 — EXIF 붙어서 커짐)
파일바이트 sha256 동일? False
픽셀해시(Pillow decode → tobytes → sha256) 동일? True
```
→ **OCR 시점 사진과 saveAct 시점 사진은 파일바이트는 달라도 디코드한 픽셀 데이터는 100% 동일.**
파일 SHA256이 아니라 **"디코드 픽셀 SHA256"**을 매칭 키로 쓰면 정확히 맞아떨어진다.
(참고: 프로덕션 백엔드에 Pillow 10.2.0 이미 설치돼 있음 — 신규 의존성 불필요)

### 왜 (b)가 아니라 (a)인가
- (a)는 APK 재빌드·배포·현장 재설치 없이 **오늘 바로** 백엔드만으로 동작.
- (b)(sample_id 왕복)는 네이티브 코드 변경 + 재배포 사이클이 필요해 후순위 확정.

## 구현 계획 (백엔드만, `cst-input/backend/app.py`)

### 1. `/api/ocr`에서 실패 표본 채집
`api_ocr()`(L632~678) 루프에서 `_extract_meter_no(lines)`가 `''`을 반환한 건에 한해,
`finally: shutil.rmtree(tmpd)`로 지우기 **전에** 아래를 "미확정 대기 풀"에 저장:
- 사진 원본 바이트(이미 `p.write_bytes()`로 디코드돼 있음 — 그대로 복사)
- `raw` 텍스트(이미 만들고 있는 `" | ".join(...)`) — 실패 원인 분석에 필요
- **매칭키 = 픽셀 SHA256**(`Image.open(p).convert('RGB').tobytes()` → sha256)
- 타임스탬프(KST), 실패사유(현재는 단일 사유뿐 — "계기번호 후보 없음". 세분화 여지는 있으나 지금은 1종류)
- 앱버전 — **폰이 안 보내는 값이라 채울 방법이 마땅치 않음.** `/api/ocr` body에 필드가 없다.
  (열린 질문 — 아래 참조)

### 2. `/api/saveact`(`_saveact_core`)에서 라벨 부착
마스터/슬레이브 각각 슬롯 "5" 사진을 `_photos_to_files()`로 디코드하는 시점(이미 파일 경로 있음)에,
같은 방식으로 픽셀 SHA256을 계산해 "미확정 대기 풀"에서 조회한다.
- 매치되면: 그 사진의 최종 확정값(`mb`=마스터 계기번호 / `s["meterNo"]`=슬레이브 계기번호 — saveAct
  시점엔 앱이 빈 값 진행을 막으므로(`CollectViewModel` L261) **반드시 작업자가 채운 값**)을 정답
  라벨로 붙여 표본을 확정 저장소로 옮긴다. 대기 풀에서는 제거(중복 매칭 방지).
- 매치 안 되면: 조용히 통과(표본 없이 saveAct만 정상 진행).
- **전체를 `try/except`로 감싸 saveAct 응답에 절대 영향 없게 한다**(요건 4).

### 3. 용량 관리 (미확정 대기 풀 한정 — 통신팀 소관)
- 상한: 개수 캡(예: 500장) 또는 총용량 캡, 초과 시 가장 오래된 것부터 삭제(FIFO).
- TTL: 오래 대기해도 saveAct가 안 오면(작업자가 그 큐 항목을 아예 안 올리거나 삭제) 영영 안 지워지는
  누적 방지 — N일 지난 미매칭 항목은 자동 폐기.
- 정확한 캡 수치/TTL은 실사용 빈도 보고 조정. 초기값 제안만 해두고 확정은 운영하며 튜닝.
- **확정(라벨 붙은) 표본의 보관 위치·용량정책은 ocr-meter 소관** — 거기로 이관 후엔 통신팀 책임 아님.

## 열린 질문 (ocr-meter/PM 확정 필요 — 임의로 정하지 않음)

1. **표본 스키마·저장 경로.** ocr-meter가 정본으로 정해달라(PM 지시대로 임의 결정 안 함).
   - 이관 방식 제안: 통신팀이 "미확정 대기 풀"에서 라벨 매칭까지 끝낸 뒤, ocr-meter가 지정한
     디렉토리/파일명 규칙에 맞춰 최종 저장. 통신팀 쪽 대기 풀 자체 경로는 자유(맥 로컬, 상세는
     구현 시 아무 경로나 — 최종 산출물 스키마만 ocr-meter 것을 따름).
2. ~~앱버전 필드~~ — **PM 결정(2026-07-27): 생략.** 앱버전을 얻으려면 폰 변경(재빌드)이 필요한데
   그건 이 설계의 최대 장점(폰 수정 0)을 깨는 비용이다. 대신 **OCR 추출 로직 식별자**(`_extract_meter_no()`
   버전/커밋 해시 등 백엔드가 이미 아는 값)를 표본 메타에 넣는다 — "어느 앱버전이 실패했나"보다
   "어느 OCR 로직이 실패했나"가 학습 관점에서 더 유용하다는 PM 판단. 구현 시 app.py에 로직버전
   상수(예: `_EXTRACT_LOGIC_VER = "e5-2026-07-14"` 류) 하나 두고 그걸 표본 메타에 싣는 방식으로 간다.
3. **crop_fail 학습큐 통합 여부** — ocr-meter 판단 사항. 통신팀은 어느 쪽이든 "확정 표본 저장" 호출부만
   맞추면 됨.
4. **원본 해상도 필요 여부, 크롭 전/후 어느 쪽** — `/api/ocr`이 받는 사진은 폰이 전송한 그대로(리사이즈
   여부는 `ImageProc` 캡처 파이프라인 확인 필요 — 별도 확인 가능, ocr-meter가 요건 명시하면 맞춤).

## 범위 확정 (PM 통보, 2026-07-27)
아미큐 표본은 **계기번호 한정**. 검침값 표본 확장은 고려하지 않는다 — 신설계기는 검침값을 읽을
구조 자체가 아니고, 검침값 LCD는 순환표시라 필요 항목이 뜰 때 세팅해서 찍어야 하는데 통신팀은
그렇게 촬영하지 않아 사진에 검침값이 없다. 검침값 표본은 계기팀(철거사진) 소관.
