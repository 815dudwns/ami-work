> 정정 이력: 2026-06-06 실측으로 원래 전제("모든 사진에서 계기번호+검침값 둘 다")가 틀려 아래로 교체됨.

## 1. 목적 — 데이터 검증 시스템 (사진 분석 아님)

OCR을 자체 학습시키는 목적은 **앞으로 들어오는 raw 데이터(작업자가 수집·입력한 계기번호·검침값)를 자동 검증**하는 것.

```
[raw 데이터 + 계기 사진]
   → 1차: OCR이 사진에서 값 읽어 입력값과 대조 (자동)
       일치 → 통과
       불일치(문제건) → 2차: 사람이 검증
```

목표 = **불일치만 사람이 보게** 1차에서 거르기. 핵심 지표는 정확도뿐 아니라 **오통과율**(틀린 값을 일치로 잘못 판정) 최소화.

## 2. 무엇을 읽어 무엇과 대조하나 — 철거/신설로 분기

| 사진 구분 | OCR이 읽을 것 | 대조 대상 | 다수 타입 | 비고 |
|---|---|---|---|---|
| **철거계기** | LCD **검침값(적산전력)** | 입력 검침값 | E(항상 철거), G | LCD에 값 안정 표시, QR 없음 |
| **신설계기** | **계기번호** | 입력 계기번호 | AMIGO | LCD는 시계 순환→검침값 안 보임. **QR 1순위**, 명판 OCR 폴백 |

- **철거/신설은 사진 업로드 시점에 이미 주어짐** → OCR이 분류 불필요. 플래그로 무엇을 읽을지만 분기.
- **E타입은 신설이 없음** = E면 항상 검침값.
- 어떤 타입으로 raw를 가져올지 미정 → 두 파이프라인 모두 준비.

## 5. 첫 단계 체크리스트

1. **데이터 정제**: 타입분류 → 신설(계기번호셋)/철거(검침값셋) 분리. 파일명 파싱으로 (이미지, 라벨) 테이블 생성. 라벨 없는 건 분리.
2. **유효프레임 필터**: 신설 AMIGO는 시계/LOAD 프레임 다수 → 계기번호 검증엔 명판/QR 영역 사용(LCD 무시). (검침값을 신설서 읽을 일은 사실상 없음)
3. **라벨 매칭 실측**: 철거 검침값은 removal_values 라이브 조회 매칭률 측정.
4. **베이스라인**: 사전학습 PP-OCRv5 그대로 — 계기번호/검침값 인식률 + **오통과율** 측정(전처리 유무 비교).
5. **파인튜닝**: 계기번호(영숫자)·검침값(7세그먼트, DSEG 합성) 분리 학습 후 재측정.
6. **검증 통합**: OCR값 vs 입력값 대조 → 신뢰도 임계로 "통과 / 애매(사람) / 불일치(사람)" 3분류. 결과를 `research/ocr_*.md`에 기록.

## 6. 기술 권장 (상세는 조사.md §3·§6)

- **PaddleOCR PP-OCRv5** 1순위(경량 5M, ONNX/안드로이드 배포, Apache 2.0).
- 계기번호(영숫자)·검침값(7세그먼트)은 **분리 학습**.
- 7세그먼트는 범용 OCR 약함 → **CLAHE 전처리 + DSEG 합성데이터 파인튜닝** 필수.
- 파이프라인: 전처리 → ROI 검출(YOLOv8/DBNet) → 인식(각각 파인튜닝) → 후처리(형식·범위 + 입력값 대조).

## 7. 제약/주의

- **종로 `ami-jongno` DB는 운영 중 — 읽기만**(라벨 추출용). 쓰기 절대 금지(메모리 `jongno_delete_protect`, 오삭제 사고 이력).
- KST 기준. 단상/삼상: 단상=E·EA·G25/26/27·Amigo53 / 삼상=G45/46/47·Amigo55.
- 계기 이미지엔 주소·고객정보 포함 가능 → 외부 OCR API 금지, 자체 모델 필수.
- 한전 적대 리스크(메모리 `awms_kepco_risk`) — 대외 노출 톤 신중.
- 파일명 지침종류는 awms 사진슬롯명일 수 있음(실제 화면과 불일치 가능) → 철거 표본으로 검증.
