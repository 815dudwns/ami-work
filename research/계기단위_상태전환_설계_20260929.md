# 상태 단위를 주소에서 계기로 — 설계 (2026-09-29)

> 영준님 지시: "주소단위가 아니라 계기단위이고, 주소로 완료를 치는 것은 그 주소의 계기그룹을
> 다 작업했다는 뜻이니 계기 하나하나 완료가 되어야 해. 개별불가 하고 완료를 쳐도 (되게).
> 모든 것을 개별불가하고 완료를 치면 주소 불가 빨간색이 유지되도록 주소 메모로 표시.
> 아니면 계기 하나하나 불가가 되게."

## 1. 지금 무엇이 있고 무엇이 없나 (실측)

`workStatus[상태키]` 스키마 — 상태키는 주소 기반(`js/status-key.js`)

| 필드 | 단위 | 있나 | 쓰이나 |
|---|---|---|---|
| `state` (`pending`/`complete`/`hold`/`fail`) | **주소(그룹)** | 있다 | **마커 색·통계 개소 집계의 유일한 근거** |
| `reason` | 주소 | 있다 | 불가·보류 사유 |
| `failedMeters{계기번호: 사유}` | **계기** | **있다** | 디테일 목록 취소선 · 통계 **계기** 집계 |
| `checkedMeters[]` | 계기 | 있다 | 작업 중 확인용 체크박스(상태 아님) |
| `added_meters{}` | 계기 | 있다 | 관리자가 추가한 계기 |
| **계기 단위 완료** | 계기 | **없다** | — |

즉 **불가는 이미 계기 단위가 있고, 완료는 없다.** 그래서:

- `js/map.js:539 aggregateState()` 는 `state` 만 집계한다. `failedMeters` 를 **안 본다.**
- `js/detail.js:1296 updateStatus('complete')` 는 `saveStateEvent(addr,'complete')` 만 부른다.
  계기별 기록을 남기지 않는다.
- 그 결과 **전 계기를 개별불가한 뒤 완료를 치면 마커가 회색(완료)** 이 된다. 영준님이 원하는
  빨강 유지가 안 된다.
- 반대로 주소 `state=fail` 이 남아 있으면, 나중에 **같은 주소에 다른 계기가 들어와도 빨강**이다
  (실측 2026-09-29: 합동 411건 중 4건 — `고산자로 454(제기동 1034)|합동` 이 9/9 '주소다름'
  불가를 9/28 신규 계기 4개가 물려받았다).

`failedMeters` 가 전체 45건뿐인 것도 이 때문이다 — 계기별로 찍어도 마커에 반영되지 않으니
현장에서 쓸 이유가 없었다.

## 2. 바꿀 것

### 2.1 계기 단위 완료 기록 신설

```
workStatus[키].meterStates = {
  "07550001231": { s: "complete", at: 1790600000000, by: "kim", byName: "김상권" },
  "07550001084": { s: "fail", r: "문잠김", at: ..., by: ..., byName: ... }
}
```

- **`failedMeters` 를 없애지 않는다.** 통계·복원 스크립트 5곳이 읽고 있고(`stats.html`,
  `scripts/upload_work_status.py`, `restore_firebase.py/js`, `migrate_status_keys.py`,
  `verify_status_key_migration.py`) 이미 찍힌 45건이 있다. `meterStates` 를 쓰면서
  **불가는 두 곳에 같이 기록**한다(쓰기 시 동기화). 다음 판에서 `failedMeters` 를 읽기 전용으로
  내린다.
- 읽을 때 우선순위: `meterStates[계기].s` → 없으면 `failedMeters[계기]` 있으면 fail → 없으면
  아래 3.1 의 하위호환 규칙.

### 2.2 주소 완료 = 그룹 전 계기 완료

`updateStatus('complete')` 를 이렇게 바꾼다.

1. 그 마커의 계기 목록(`currentMeters` + `added_meters`)을 훑는다
2. **이미 불가로 찍힌 계기는 건드리지 않는다** — 불가 유지
3. 나머지 전부 `meterStates[계기] = {s:'complete'}`
4. 주소 `state` 는 아래 2.3 규칙으로 **파생**한다(사람이 직접 쓰는 값이 아니게 된다)

### 2.3 주소 상태는 계기 상태에서 파생한다

| 계기 구성 | 주소 `state` | 마커 색 | 비고 |
|---|---|---|---|
| 전부 `complete` | `complete` | 회색 | |
| **전부 `fail`** | **`fail`** | **빨강** | **주소 메모에 "전 계기 불가" + 사유 요약 표시** |
| 일부 `fail` + 나머지 전부 `complete` | `complete` | 회색 | 불가 계기는 디테일에서 취소선·사유 |
| 하나라도 기록 없음(신규 계기 포함) | `pending` | 원래 색 | **새 계기가 들어오면 자동으로 미착수로 돌아온다** |
| `hold` 가 섞이면 | `hold` | 파랑 | 보류는 주소 단위로 유지(계기별 보류는 만들지 않는다) |

★이 표가 이번 변경의 핵심이다. `aggregateState()` 가 `state` 를 읽는 대신 **계기 상태를
집계**하도록 바꾼다.

### 2.4 개별불가 버튼이 실제로 기능하게

버튼·입력·저장 경로(`toggleMeterFail`·`saveMeterFailReason`)는 **이미 정상 동작한다.**
바꿀 것은 그 결과가 마커·주소 상태에 반영되게 하는 것(2.3)과, 불가 찍은 뒤 **완료를 쳐도
불가가 살아남게** 하는 것(2.2-2)뿐이다. UI 는 손대지 않는다.

## 3. 옛 기록 처리 — 두 안 (★영준님 선택 필요)

`workStatus` 21,950키(합동 5,311 · 완료 20,602 · 불가 883)에는 **당시 계기 목록이 없다.**
그래서 옛 `state='complete'` 를 계기별로 펼칠 수 없다.

### A안 — 하위호환 유지 (안전, 기본 권장)

`meterStates` 가 없는 키는 **종전대로 `state` 를 그대로 쓴다.** 새로 찍는 것만 계기 단위.

- 장점: 기존 기록 100% 보존, 마이그레이션 없음, 되돌리기 쉬움
- 단점: **영준님이 발견한 문제(새 계기가 옛 완료·불가를 물려받음)가 옛 키에는 남는다**

### B안 — A안 + 등재일 게이트

A안에 한 줄 더: 옛 기록의 `updatedAt` 이 **그 계기의 리스트 등재일보다 이르면 무시**한다
(합동은 `작업일`/`WORK_DATE`, 미청구는 `최종시공일`이 있다).

- 장점: 옛 키의 오염까지 해소. 9/28 신규 4건이 바로 정상으로 돌아온다
- 단점: 등재일이 없는 데이터셋(실효 `site-data`)은 게이트를 못 걸어 A안과 같다
- 위험: 등재일이 **앱 작성 시각**이라 실제 작업일과 다를 수 있다([[time_order_not_exclusion_axis]]).
  다만 여기서는 '제외 판정'이 아니라 '표시 우선순위'라 틀려도 작업분이 사라지지 않는다

## 4. 영향 범위 (건드릴 파일)

| 파일 | 무엇 |
|---|---|
| `js/map.js` | `aggregateState()` 를 계기 집계로 · 마커 색 판정 2곳(686·776) |
| `js/detail.js` | `updateStatus()` 완료 전파 · `resetStatus()` 계기 상태도 초기화 · 주소 메모에 '전 계기 불가' 표시 |
| `js/firebase.js` | `meterStates` 이벤트 타입 추가 · 델타 머지에 포함 · `failedMeters` 동시 기록 |
| `stats.html` | 개소·계기 집계를 계기 상태 기준으로(2패스 구조는 이미 있어 교체만) |
| `scripts/status_key.py` | 변경 없음(키 규칙 불변) |
| `scripts/upload_work_status.py` · `weekly_workstatus_merge.py` | `meterStates` 보존(머지에서 안 날아가게) |
| `scripts/restore_firebase.py` | 백업·복원에 `meterStates` 포함 |

★**상태키 규칙은 건드리지 않는다.** 키를 바꾸면 기존 21,950건이 전부 고아가 된다.
계기 단위는 **키 안의 필드**로 해결한다.

## 5. 테스트 (구현 후 반드시)

로컬 `http://localhost:8080` + 폰 실기기 2대(다중 작업자 동기화 확인).

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 계기 5개 주소에서 완료 클릭 | 5개 전부 `meterStates.complete` · 마커 회색 |
| 2 | 계기 2개 개별불가 → 완료 클릭 | 불가 2개 유지 · 나머지 3개 완료 · 마커 **회색** · 디테일에 취소선 2줄 |
| 3 | **계기 5개 전부 개별불가 → 완료 클릭** | 마커 **빨강 유지** · 주소 메모에 '전 계기 불가' + 사유 |
| 4 | 3번 상태에서 계기 1개 불가해제 | 마커 pending 또는 회색으로 전환(그 계기 기록 없음) |

| 8 | 통계 대조 | 개소·계기 합이 변경 전후로 설명 가능(줄면 이유 제시) |
| 9 | 옛 키(마이그레이션 없는 것) 열기 | A안대로 종전 상태 그대로 보임 |

★**8번이 게이트다.** 통계가 조용히 깎이면 배포하지 않는다([[suspect_favorable_measurement]]).

## 6. 진행 순서

1. 이 문서 승인 + 3장 A/B 선택
2. 통신팀 데스크에 발주(아미맵 실무 소관)
3. 구현 → 로컬 테스트 9항목 → PM 검수
4. **테스트 배포는 관리자 계정만 보이는 상태로** 하지 않는다 — 데이터 구조 변경이라
   전 작업자에게 한 번에 간다. 그래서 **백업 먼저**(`scripts/restore_firebase.py` 용 스냅샷)
5. 배포 후 현장 1일 관찰 → 이상 없으면 `failedMeters` 읽기 전용 전환 계획

## 7. 결정 필요 (영준님)

1. **3장 A안 / B안** — 옛 기록을 그대로 둘지, 등재일 게이트까지 걸지
2. **일부 불가 + 나머지 완료일 때 마커 색** — 위 표는 회색(완료)으로 잡았다.
   "불가가 하나라도 있으면 눈에 보여야 한다" 면 회색에 빨간 테두리 같은 구분을 줄 수 있다
3. **보류(hold)를 계기 단위로도 만들지** — 위 표는 주소 단위 유지로 잡았다
4. **통계 개소 집계** — 지금은 "전 세대 완료일 때만 개소 완료". 계기 단위로 바뀌면
   같은 규칙을 계기 상태로 계산한다(결과는 거의 같아야 한다). 다르게 하길 원하면 말씀
