# AMI 지식 재구조화 설계 (2026-07-13)

> 영준님 지시: 우리 핵심 시스템 지식을 시스템(도메인) 단위로 정리·분리. 상위/공용 지식(계기타입·통신팀·계기팀 등)을 코어로 올리고, 이제까지의 모든 md·옵시디언 파일을 시스템별로 재봉합. 앞으로 HANDOFF·스킬에서 각 시스템이 내린 결정도 계속 흡수.
>
> **왜**: 무언가를 시켰을 때 그 시스템에만 들어가거나, 독립 PM처럼 유연하게 작동하도록. 지금은 뭘 시켜도 거대 CLAUDE.md 전체 + 메모리 116개가 통째로 깔림.
>
> 이 문서 = 승인용 설계안. 실제 이동·생성은 이 문서 승인 후 단계별 실행.

## 0. 현황 진단 (매핑 결과)

총 **269개** 문서가 **성격별 3분할**로 흩어짐 → 한 시스템 지식이 세 곳에 쪼개짐:
- **repo 107** = 기술 레퍼런스 (research/ 중심)
- **auto-memory 116** = 운영 함정·교훈 (단문, Claude 자동 recall)
- **옵시디언 46** = 세션로그(32)·전략·매뉴얼

목표 = **성격축 → 도메인축 전환**. 계기큐 지식이면 repo프로세스+메모리함정+로그가 "계기큐" 하나로 모임.

## 3. "독립 서브PM" 실체

각 L1~L3 시스템 = 하나의 서브PM 소환 단위. 서브PM은 자기 시스템 카드(4요소) + L0 공용코어만 로드하면 독립 작동.
- 예: "계기큐 버그" → 계기큐 카드 + awms공통 + L0 → 계기팀 서브PM
- 예: "종로맵 통계 수정" → 종로맵/통계 카드 + L0 → 종로맵 서브PM
- ami-pm(메인)은 조율·분배만. spawn 스킬에 시스템별 서브PM 추가 검토(2차).

## 4. 옵시디언 ↔ repo ↔ 메모리 3층 경계 (★보류했던 것 — 제안)

핵심 난제: auto-memory 116개는 Claude가 세션마다 **자동 recall**하는 자산. 통째 옵시디언 이전 시 자동 로드 상실. → 폐지가 아니라 **역할분담 3층**을 제안:

| 층 | 무엇 | 대상 | 읽는 주체 |
|---|---|---|---|
| **옵시디언 볼트** | 지식 **정본** (4요소 본문·결정이력·로그·매뉴얼) | `Projects/AMI/core/`, `Projects/AMI/systems/<시스템>/` | 사람 + 서브PM(참조 로드) |
| **repo CLAUDE.md** | Claude **로드용 압축** (코드 옆) | 각 코드폴더에 얇은 CLAUDE.md = 3~5줄 요약+핵심함정+옵 정본링크. 루트 CLAUDE.md는 인덱스로 슬림화 | Claude(작업 시) |
| **auto-memory** | Claude **자동 recall** (원자적 사실·함정) | 유지하되 **시스템 태깅**. 옵 카드가 관련 메모리를 링크 | Claude(자동) |

즉 **메모리=Claude용 원자사실 / 옵카드=사람·서브PM용 종합 / repo CLAUDE.md=작업 진입점**. 이중화가 아니라 계층. 메모리와 옵카드는 링크로 연결(메모리 slug ↔ 옵 카드).

→ **이 3층 경계안 확인 필요** (§8 Q1).

## 7. 마이그레이션 단계 (승인 후)

1. **골격 생성**: 옵시디언 `Projects/AMI/core/`·`systems/` 폴더 + 빈 시스템 카드 13개(템플릿) + repo 인덱스 초안
2. **L0 공용코어 먼저**: 계기도메인·팀구분·데이터규칙·사업구조·awms공통 카드 채움 (영준님 예시 = 최우선)
3. **시스템별 봉합**: 시스템 1개씩 repo+메모리+로그 → 카드 4요소로 종합. 메모리는 태깅+링크(폐지 아님)
4. **repo CLAUDE.md 슬림화**: 각 코드폴더 얇은 CLAUDE.md + 루트 인덱스화. 경로참조 갱신(§ 진단문서의 참조맵)
5. **정리대상 처리** (§6)
6. **서브PM 배선**: spawn/에이전트에 시스템별 진입점 (2차)

각 단계 커밋 분리. 옵시디언은 obsidian-writer 위임, repo는 직접.
