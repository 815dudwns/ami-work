# 안드로이드 백그라운드 안정 실행 전략

> 작성일: 2026-06-15
> 대상: 삼성 갤럭시 A31~A33 (Android 11~15 혼재), 사내 배포(Play 정책 무관)
> 문제: 보조앱(WorkManager 네이티브 업로드) + 계기큐(WebView fetch 일괄)
>

## 1. 삼성 OEM 백그라운드 제약 실태

### 1-1. 제약 레이어 (중요도 순)

삼성 기기에서 백그라운드 실행을 막는 레이어는 **3가지가 독립적으로 작동**한다.

| 레이어 | 구현체 | 제어 가능? |
|---|---|---|
| AOSP Doze / App Standby | Android OS 공통 | 화이트리스트로 부분 해제 |
| 삼성 OEM 배터리 절전 (Good Guardians) | One UI Battery Guardian | 앱별 "절전 해제" 설정 필요 |
| 삼성 "앱 절전(sleeping apps) / 딥슬립" | One UI 독자 구현 | "절대 절전 안 함" 목록에 추가 |

**핵심 주의**: 이 3가지는 **독립적**이다. AOSP 배터리 최적화 예외로 화이트리스트에 등록해도 삼성의 "sleeping apps" 레이어가 별도로 앱을 죽일 수 있다.
(출처: dontkillmyapp.com/samsung, 2026-06-09 업데이트)

### 1-2. 삼성 sleeping apps 동작 방식

- **Sleep 모드**: 일정 시간 미사용 앱을 백그라운드에서 일시 중단
- **Deep Sleep**: "절대 백그라운드 실행 안 함" — 앱 열 때만 동작
- **Never sleeping apps**: 목록 추가 시 백그라운드 실행 항상 허용

삼성은 Android P 이후 더 공격적으로 앱을 종료하며, 3일 미사용 앱은 백그라운드 시작이 불가능해질 수 있다 (알람 앱 등 피해). **펌웨어 업데이트 후 설정이 초기화되거나 재추가될 수 있다.**
(출처: dontkillmyapp.com/samsung)

### 1-3. Android 11 삼성 특이사항

Samsung은 Android 11에서 **포그라운드 서비스 중에도 WakeLock을 차단**하는 비표준 제약을 도입했다. 이로 인해 헬스앱 등에서 센서 데이터 수집 실패가 보고됐다.
(출처: dontkillmyapp.com/samsung)

### 1-4. Samsung + Android 14 화해 (중요 변화 — 우리 앱에 이미 적용됨)

Samsung은 One UI 6.0 (Android 14) 타겟팅 앱에 대해 공식 발표:

> "Since One UI 6.0, foreground services of apps targeting Android 14 will be guaranteed to work as intended so long as they are developed according to Android's new foreground service API policy."
> — Samsung 공식 성명 (출처: medium.com/@domen.lanisnik/guide-to-foreground-services-on-android-14)

즉, **targetSdkVersion=34(또는 35) + 올바른 FGS 타입 선언** 시 Samsung OEM의 비표준 백그라운드 킬이 면제된다.

**우리 앱은 이미 targetSdk=35 — 이 보장이 활성화 상태.** 추가 SDK 범프 없이 올바른 FGS 타입 선언만 확인하면 된다.

단, **"앱 절전" 레이어는 이 보장 범위 외일 수 있다** (사용자가 직접 Deep Sleep에 추가 시). 사내 배포이므로 기기 프로비저닝 시 한 번만 "절대 절전 안 함" 설정으로 해결 가능하다.

## 2. WorkManager setExpedited 동작 상세

### 2-1. setExpedited 란

`WorkRequest.setExpedited(OutOfQuotaPolicy)`는 WorkManager에게 "이 작업을 최대한 빨리 실행하라"고 지시한다. **작업이 언제 시작되느냐(스케줄링)** 에 영향을 준다. `setForegroundAsync()`는 **이미 시작된 워커가 얼마나 오래 살아남느냐**에 영향을 준다. 둘은 별개.

현재 보조앱의 문제("백그라운드 가면 안 시작")는 정확히 **스케줄링 지연** 문제이므로 `setExpedited`가 핵심 레버다.
(출처: developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

### 2-2. App Standby Bucket별 expedited 쿼터

| Standby Bucket | Expedited 쿼터 | Regular Job 쿼터 | 네트워크 |
|---|---|---|---|
| Active | 30분/24시간 | 20분/60분 롤링 | 무제한 |
| Working Set | 15분/24시간 | 10분/4시간 롤링 | 무제한 |
| Frequent | 10분/24시간 | 10분/12시간 롤링 | 무제한 |
| Rare | 10분/24시간 | 10분/24시간 | 비활성화 |
| Restricted (Android 12+) | 5분/24시간 | 10분/24시간 | 비활성화 |

(출처: developer.android.com/topic/performance/power/power-details)

**쿼터 소진 시**: `OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST` 설정 시 일반 작업으로 강등되어 버킷 규칙에 따라 지연 실행. `DROP_WORK_REQUEST`는 작업 자체를 취소.

**쿼터 회복**: 앱이 Active 또는 Working Set 버킷으로 올라가면 쿼터가 회복된다. 매일 자동 갱신.

### 2-3. Android 버전별 setExpedited 동작

| Android 버전 | setExpedited 동작 | 비고 |
|---|---|---|
| Android 11 (API 30) 이하 | 미지원 — WorkManager가 FGS로 폴백 | `getForegroundInfoAsync()` 구현 필수 |
| Android 12 (API 31)+ | 네이티브 expedited job 지원 | quota 초과 시 OutOfQuotaPolicy 적용 |
| Android 12+ + 화이트리스트 | 즉시 실행 보장 | Doze 유지보수 윈도우 무관 |

**A31(Android 11) 주의**: `setExpedited` 호출 시 WorkManager 2.7+ 에서 자동으로 FGS로 폴백한다. 이 경우 `getForegroundInfo()` 가 없으면 런타임 크래시. **보조앱 WorkerClass에 `getForegroundInfo()` 오버라이드 필수.**
(출처: developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

### 2-4. 삼성에서 setExpedited 단독으로 충분한가

**충분하지 않다**. Expedited job은 OS 레벨 쿼터를 받아도 삼성 OEM 레이어(sleeping apps, Battery Guardian)가 추가로 차단할 수 있다. setExpedited + 배터리 최적화 화이트리스트 + 삼성 절전 앱 목록 제외 를 **세트**로 적용해야 신뢰성이 높아진다.

## 3. REQUEST_IGNORE_BATTERY_OPTIMIZATIONS

### 3-1. 효과

배터리 최적화 화이트리스트 등록 시:
- **Doze 상태에서도 네트워크 사용 + 부분 WakeLock 허용**
- App Standby 버킷 제한에서 부분 면제
- WorkManager Job 및 AlarmManager 실행 허용

**중요**: "부분 면제"다. 삼성 OEM 레이어(sleeping apps)는 **별도로 제어**해야 한다.
(출처: developer.android.com/training/monitoring-device-state/doze-standby)

### 3-2. 코드로 1회 팝업 띄우는 표준 방법

```kotlin
// AndroidManifest.xml
<uses-permission android:name="android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS"/>

// Activity 또는 onboarding 시점에 1회 요청
val pm = getSystemService(Context.POWER_SERVICE) as PowerManager
if (!pm.isIgnoringBatteryOptimizations(packageName)) {
    val intent = Intent(Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS).apply {
        data = Uri.parse("package:$packageName")
    }
    startActivity(intent)
}
```

(출처: developer.android.com/training/monitoring-device-state/doze-standby)

### 3-3. Play 스토어 정책 리스크

Play 스토어는 이 permission을 선언한 앱에 대해 "합당한 이유 없이 사용" 시 정책 위반 처리한다. **우리는 사내 배포(Play 외부)라 무관**. 제약 없이 사용 가능.

### 3-4. 삼성에서의 실효성

배터리 최적화 예외가 AOSP Doze를 완화하지만, 삼성의 추가 레이어(sleeping apps, App Power Saving)는 **별도로 사용자가 설정**해야 한다. 코드로 제어 불가능한 부분이 존재한다.

### 3-5. 삼성 "절대 절전 안 함(Never sleeping)" 설정 (사용자 조작)

설정 > 배터리 > 앱 절전 > "절대 절전 안 함" > 앱 추가

이 단계를 사용자에게 온보딩 화면에서 안내해야 한다. 코드로 자동화 불가능.

## 4. FGS vs WorkManager+setForeground vs Expedited Work 비교

### 4-1. 사진 업로드(수초~수십초, 즉각성 중요) 케이스에 적합한 방식

| 방식 | 즉시 실행 | 백그라운드 지속 | 코드 복잡도 | 비고 |
|---|---|---|---|---|
| 진짜 FGS (Foreground Service) | O (startForeground) | O (OS 보호) | 높음 | 가장 신뢰성 높음 |
| WorkManager + setExpedited | O (쿼터 있을 때) | X (워커 생명주기) | 낮음 | 쿼터 소진 시 지연 |
| WorkManager + setForegroundAsync | O (시작 후) | O (FGS로 승격) | 중간 | 시작 자체는 지연될 수 있음 |
| 일반 WorkManager | X | X | 낮음 | 백그라운드 지연 |

**권장**: 즉각성이 중요한 사진 업로드에는 `setExpedited + setForegroundAsync 조합`이 실용적. 더 강한 보장이 필요하면 진짜 FGS.

### 4-2. Android 14/15 FGS 타입 제약 (dataSync)

**Android 14 (API 34)**:
- FGS 타입 명시 필수 (manifest `android:foregroundServiceType`)
- `dataSync` 타입에는 `FOREGROUND_SERVICE_DATA_SYNC` 권한 필요
- 타겟 34+ 앱은 FGS 시작 시 타입 누락 시 `SecurityException`

**Android 15 (API 35)**:
- `dataSync` FGS는 **24시간 내 합산 6시간** 제한
- 6시간 초과 시 `Service.onTimeout(int, int)` 호출 (Android 15 신규)
- onTimeout 내에서 서비스 중단 안 하면 ANR 또는 `RemoteServiceException` 발생
- 타이머는 **앱이 포그라운드로 오면 리셋** (사용자가 앱 열면 초기화)
- 6시간 제한은 앱의 모든 dataSync FGS가 공유

(출처: developer.android.com/develop/background-work/services/fgs/timeout, developer.android.com/about/versions/15/behavior-changes-15)

**우리 케이스(단건 사진 업로드)는 6시간 제한에 걸릴 일이 없다**. 단, 다수를 연속으로 처리하는 경우 누적 추적 필요.

### 4-3. getForegroundInfo() 오버라이드 필요 여부

```kotlin
// Android 11(API 30) 이하 지원 시 필수
override suspend fun getForegroundInfo(): ForegroundInfo {
    return ForegroundInfo(
        NOTIFICATION_ID,
        createNotification(), // NotificationCompat.Builder로 생성
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q)
            ServiceInfo.FOREGROUND_SERVICE_TYPE_DATA_SYNC
        else 0
    )
}
```

A31(Android 11) 기기가 있으므로 **반드시 구현해야** 한다.

## 5. Android 15 백그라운드 네트워크 차단 실체

### 5-1. "백그라운드 1분 후 소켓 끊김" 관찰의 실제 원인

유저가 관찰한 "화면 OFF 후 네트워크 끊김"의 실체는 단일 원인이 아닌 **3가지 메커니즘의 합산**이다.

| 메커니즘 | 트리거 | 네트워크 영향 |
|---|---|---|
| AOSP Doze (Light Doze) | 화면 OFF + 정지 ~수분 | 네트워크 차단, maintenance window만 허용 |
| Cached App Freezer | 앱이 cached 상태 진입 | CPU 0%, 네트워크 전면 차단 (Android 12+, 일부 기기) |
| 삼성 OEM 절전 | 삼성 자체 정책 | 프로세스 킬 또는 네트워크 차단 |

**Cached App Freezer** (Android 12~15, Pixel/일부 기기 실측):
- cached 프로세스(=백그라운드)를 freezing하여 CPU 사용 0%
- **FGS가 실행 중이면 프로세스는 cached 상태가 아니므로 Freezer 적용 안 됨**
- FGS 없는 앱이 백그라운드에서 네트워크 요청 시 freeze될 수 있음

(출처: source.android.com/docs/core/perf/cached-apps-freezer)

### 5-2. Android 15에서 실제로 바뀐 것

**명확히 바뀐 것 (targetSdk 35)**:
1. `dataSync` FGS 6시간 시간제한 + `onTimeout()` 콜백
2. `SYSTEM_ALERT_WINDOW` 단독으로는 백그라운드 FGS 시작 불가 (가시적 오버레이 창도 필요)
3. `BOOT_COMPLETED` 리시버에서 일부 FGS 타입 시작 제한
4. `mediaProcessing` FGS 타입 추가 (역시 6시간 제한)

(출처: developer.android.com/about/versions/15/behavior-changes-15)

**"백그라운드 N초 후 네트워크 소켓 강제 차단"은 Android 15 공식 문서에 명시된 변경 아님**. 관찰된 간헐 실패는 Doze + Cached App Freezer + 삼성 OEM 복합 작용으로 설명된다.

### 5-3. FGS가 떠 있으면 Doze 네트워크 면제?

**아니오 (조건부)**. 공식 문서와 실측 보고 종합:

- Doze는 네트워크 차단이 기본값. FGS가 있어도 **화이트리스트 없으면** 네트워크 차단될 수 있음
- 구글 공식 문서: "foreground services receive higher priority, although network usage may still be limited"
- **삼성 S6/S7(Android 6.x)에서 FGS 있어도 Doze 시 네트워크 끊어짐 실측** (issuetracker.google.com/issues/37070074)
- 화이트리스트 앱은 Doze에서도 "네트워크 사용 + 부분 WakeLock" 허용

**결론: FGS + 배터리 최적화 화이트리스트 세트 적용 필요.**

### 5-4. targetSdk를 낮추면 회피 가능한가

**대부분 아니다**. Doze/App Standby/OEM 킬은 **디바이스 레벨** 동작으로 targetSdk와 무관하게 적용된다. targetSdk가 게이트하는 건:
- 일부 API 동작 변경 (예: dataSync 6시간 제한은 targetSdk 35 적용)
- 특정 권한 요구사항 (FGS 타입 선언은 targetSdk 34)

따라서 targetSdk를 낮춰 6시간 제한은 피할 수 있지만, Doze/OEM 네트워크 차단은 피할 수 없다.

### 5-5. WebView fetch vs 네이티브 OkHttp에 각각 적용 방식

| | WebView fetch | 네이티브 OkHttp |
|---|---|---|
| Doze 네트워크 차단 | 적용됨 | 적용됨 |
| Cached App Freezer | 적용됨 (Chromium 포함) | 적용됨 (프로세스 공유) |
| FGS 있을 때 | Chromium JS freeze 회피 불가 (화면 OFF 시) | freeze 없음, 네이티브 실행 |
| 화이트리스트 효과 | 간접 (Doze 해제) | 직접 효과 |

WebView fetch는 화면 OFF 시 `document.visibilityState='hidden'`으로 Chromium이 JS 타이머·fetch를 throttle/suspend한다. 이건 **FGS와 관계없이** Chromium 렌더 엔진 자체의 동작이다.

## 6. 계기큐 WebView Freeze 근본 해결

### 6-1. 현재 C안(오버레이 WebView)의 한계

`TYPE_APPLICATION_OVERLAY` 창에 WebView를 붙여 화면이 켜진 상태에서 다른 앱 사용 시는 `visibilityState='visible'` 유지 — 이 케이스는 해결됨.

**화면 OFF 시**: 오버레이 창이 있어도 Chromium이 화면 off를 감지해 JS를 throttle한다. 오버레이는 "다른 앱 포그라운드"를 해결하는 것이지, "화면 OFF"는 해결하지 못한다.

### 6-2. (a) OkHttp 이관 안정성 + 쿠키 공유 가능성

**안정성**: OkHttp는 네이티브 코드로 동작하며 Chromium JS 엔진의 suspend 영향을 받지 않는다. FGS 아래서 실행 시 화면 OFF + Doze 상태에서도 안정적으로 동작한다 (배터리 최적화 화이트리스트 전제).

**awms 세션 쿠키(JSESSIONID) 공유 가능성**:
- `android.webkit.CookieManager.getInstance().getCookie(url)`로 WebView의 httpOnly 쿠키 포함 전체 쿠키 문자열 읽기 가능
- OkHttp의 `CookieJar`에서 이 값을 파싱해 사용 가능

```kotlin
// WebView 쿠키 → OkHttp 공유 패턴
val webviewCookies = CookieManager.getInstance().getCookie("https://awms.kdn.com")
// webviewCookies = "JSESSIONID=xxx; other=yyy"
// OkHttp 요청 시 Cookie 헤더로 직접 주입
val request = Request.Builder()
    .url(url)
    .addHeader("Cookie", webviewCookies ?: "")
    .build()
```

(출처: developer.android.com/reference/android/webkit/CookieManager, gist.github.com/jesty/e934314cae3d2014c6fa46ab64f3904e)

**작업량/위험**:
- awms.kdn.com의 API 엔드포인트, 파라미터, 응답 구조를 OkHttp로 재구현 필요
- awms 세션 만료 시 재로그인 로직 필요 (WebView 로그인과 세션 동기화)
- CSRF 토큰 처리 필요 여부 확인 필요
- 작업량: 중~대 (기존 JS 로직을 Kotlin으로 포팅)

### 6-3. (b) 오버레이(C안)로 화면 OFF까지 커버 가능한가

**불가능**. 오버레이 창 가시성과 무관하게 화면이 꺼지면 Chromium은 배경 탭/창 처리로 JS를 throttle한다. 오버레이는 "다른 앱 전환 시 Activity의 `onStop()`을 막아 WebView를 `VISIBLE` 상태로 유지"하는 것인데, 화면 자체가 꺼지면 Chromium 수준에서 다른 경로로 suspend된다.

### 6-4. (c) 조합 권장

```
단기(화면 ON + 다른 앱): 현재 C안 유지
화면 OFF 대응: 네이티브 OkHttp + FGS 이관
```

두 케이스를 나눠서 구현하거나, OkHttp 이관으로 통합한다.

## 8. 통합 권장 아키텍처

### 8-0. 사내 배포 우위 활용 — 기기 프로비저닝 체크리스트

우리는 사내 배포이며 기기 사용자(user01~05)를 알고 있다. 온보딩 팝업에 의존하지 않고 **기기 프로비저닝(배포 시 1회 설정)** 으로 영구 해결 가능.

**기기당 1회 수행 (adb 또는 직접 설정)**:

```bash
# 배터리 최적화 예외 설정 (adb)
adb shell dumpsys deviceidle whitelist +com.your.package.name

# 삼성 앱 절전 설정 확인 (수동 안내)
# 설정 > 배터리 > 앱 절전 > 절대 절전 안 함 > 앱 추가
```

또는 온보딩 화면에서 사용자에게 1회 안내 + 체크 저장.

### 8-1. 보조앱 (WorkManager 네이티브 업로드) 최종 권장

**레이어 1 — 배터리 최적화 화이트리스트 (즉시 적용 가능)**

```kotlin
// 앱 최초 실행 시 온보딩 단계에서
val pm = getSystemService(Context.POWER_SERVICE) as PowerManager
if (!pm.isIgnoringBatteryOptimizations(packageName)) {
    startActivity(Intent(Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS).apply {
        data = Uri.parse("package:$packageName")
    })
}
```

**레이어 2 — FGS 타입 선언 확인 + setExpedited + getForegroundInfo (낮은 작업량)**

targetSdk=35이므로 Samsung One UI 6.0 FGS 보장 활성화. 그러나 FGS 타입이 manifest에 올바르게 선언되어 있어야 보장이 적용된다.

```xml
<!-- AndroidManifest.xml — 이게 없으면 Android 14+ 에서 SecurityException -->
<service android:name=".PhotoUploadWorkerFGS"
    android:foregroundServiceType="dataSync" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_DATA_SYNC"/>
```

```kotlin
// WorkRequest 변경
val request = OneTimeWorkRequestBuilder<PhotoUploadWorker>()
    .setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 15, TimeUnit.SECONDS)
    .build()

// Worker 클래스에 추가
override suspend fun getForegroundInfo(): ForegroundInfo {
    return ForegroundInfo(
        NOTIFICATION_ID,
        createUploadNotification(),
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q)
            ServiceInfo.FOREGROUND_SERVICE_TYPE_DATA_SYNC
        else 0
    )
}
```

**레이어 3 — 온보딩에서 삼성 절전 해제 안내 (필수, 자동화 불가)**

앱 온보딩 화면에서 사용자에게 단계별 안내:
1. 설정 > 배터리 > 배터리 최적화 > "제한 안 함" 설정
2. 설정 > 배터리 > 앱 절전 > "절대 절전 안 함" 목록에 앱 추가

**우선순위/작업량/위험**:
- 레이어 0 (프로비저닝): 즉시, 작업량 극소 — 사내 배포 전체 해결의 기반
- 레이어 1 (화이트리스트): 즉시 적용, 작업량 소 — Doze 면제
- 레이어 2 (FGS 타입 + setExpedited): 1~2일, 작업량 소 — Samsung 보장 활성화 + 시작 지연 해소
- 레이어 3 (삼성 절전 해제 안내): 온보딩 또는 프로비저닝 시 — OEM 레이어 대응
- 합산 위험: 낮음. 기존 WorkManager 구조 유지하며 점진 적용 가능

**검증 방법**: 적용 후 실기기(A33 + A31)에서 화면 OFF → 30초 대기 → 사진 업로드 enqueue → 완료 여부 로그 확인. setExpedited 단독으로 해결 안 되면 setForegroundAsync 호출 추가(= FGS 승격 강제)가 다음 단계.

**Android 11 A31 주의사항**: `getForegroundInfo()` 없이 `setExpedited()` 호출 시 **런타임 크래시**. 반드시 같이 구현해야 한다.

### 8-2. 계기큐 (WebView fetch 일괄) 최종 권장

**단기: 현재 C안(오버레이) 유지 + 배터리 화이트리스트 온보딩**

화면 ON 상태에서 다른 앱 전환 케이스는 이미 C안으로 해결. 화이트리스트 추가로 Doze maintenance window 확보.

**중기: 네이티브 OkHttp 이관 (화면 OFF 완전 해결)**

```
목표: WebView에서 로그인만, 실제 API 호출은 OkHttp

구현 단계:
1. WebView 로그인 완료 후 CookieManager.getInstance().getCookie("https://awms.kdn.com")
   로 JSESSIONID 추출
2. OkHttp CookieJar에 WebView 쿠키 동기화
3. FGS 또는 WorkManager(setExpedited) 안에서 OkHttp로 fetch 실행
4. 세션 만료 시 WebView에서 재로그인 → 쿠키 갱신
```

진짜 FGS와 결합:
```kotlin
// AndroidManifest.xml
<service android:name=".AwmsQueueService"
    android:foregroundServiceType="dataSync"/>

// Service 내에서 OkHttp + CookieManager 호출
startForeground(NOTIF_ID, notification, FOREGROUND_SERVICE_TYPE_DATA_SYNC)
// OkHttp 호출로 awms API 처리
```

**Android 15 주의**: targetSdk=35이므로 FGS를 백그라운드에서 시작하려면 가시적 오버레이 창(C안)이 먼저 떠 있어야 한다. 이미 C안이 구현되어 있으므로 오버레이가 visible 상태일 때 FGS를 시작하면 `ForegroundServiceStartNotAllowedException` 발생하지 않는다. 단, 오버레이가 닫힌 상태에서 백그라운드 FGS 시작 시도는 실패할 수 있다.

**작업량**: 중~대 (Kotlin으로 awms JS 로직 포팅 필요)
**위험**: awms API 구조 변경 시 네이티브 코드도 함께 변경 필요. JS 로직이 단일 출처면 유지보수 이중화.
**위험 경감**: JS와 OkHttp를 병렬로 유지하고 화면 OFF 시에만 OkHttp 경로 사용하는 하이브리드 방식 가능.

### 8-3. 두 앱 공통 — 강도별 조치표

| 조치 | 효과 | 작업량 | 삼성 A31~A33 커버리지 |
|---|---|---|---|
| 배터리 최적화 화이트리스트 온보딩 | Doze 네트워크 허용 | 소 | 모든 버전 |
| 삼성 절전 해제 안내 | OEM 레이어 해제 | 소 (UI) | 삼성 전용 |
| WorkManager setExpedited + getForegroundInfo | 시작 지연 해소 | 소 | Android 11+ |
| WorkManager setForegroundAsync | 워커 지속 보호 | 소 | Android 11+ |
| 진짜 FGS (startForeground) | 가장 강한 보호 | 중 | 모든 버전 |
| OkHttp 이관 (계기큐) | WebView freeze 근본 해결 | 대 | 모든 버전 |
