## 요약: 핵심 설계 축 (이 문서 전체를 관통하는 원칙)

현재 시스템의 세 가지 문제(데이터 원본 보기와 검증 분리 / 배치 검증이라 최신 반영 안 됨 / "검증 탭"이 조회 도구가 아닌 전용 도구처럼 느껴짐)는 하나의 설계 결정으로 동시에 해결 가능하다.

**가벼운 규칙 검증은 쓰기 경로(on-write)에, 무거운 OCR/AI 검증은 비동기 잡(job)으로 분리하되 — 두 결과 모두 기본 데이터 그리드의 "검증 상태 열(derived status column)"에 표면화한다.**

그리드 자체가 데이터 브라우저이자 검증 리뷰어가 되면: (1) 원본 보기와 검증이 하나의 화면이 되고 (2) 규칙 검사는 즉시 반영되며 (3) 화면이 "검증 전용"이 아니라 "데이터 원본 관리" 화면으로 느껴진다.

아래 5개 섹션은 이 설계 축의 근거를 구체적 제품·패턴으로 뒷받침한다.

## 1. 스프레드시트형 데이터 그리드 + 인라인 유효성 검사 패턴

### 1.1 AG Grid — 마스터-디테일 + 셀 단위 검증

**제품**: AG Grid (JavaScript Enterprise Grid)
**출처**: https://www.ag-grid.com/javascript-data-grid/master-detail/

AG Grid의 마스터-디테일(Master Detail) 패턴은 마스터 행을 클릭/확장하면 인라인 서브 그리드 또는 커스텀 패널이 열리는 구조다. 본 포털의 데이터 단위(daily_seq = 하나의 교체 이벤트 = 철거계기번호 + 신설계기번호 + 검침값 4개 + 사진들)는 이 구조와 정확히 매핑된다.

**유효성 검사 메커니즘**:
- `cellClassRules`: 셀 단위로 규칙 함수를 등록하면 조건이 참일 때 CSS 클래스가 자동으로 적용된다. 예) 계기번호 길이 !== 11이면 빨간 배경.
- `valueSetter` + `valueParser`: 값이 셀에 입력되는 시점에 즉시 형식 검증, 변환, 거부(취소)가 가능하다.
- 동기/비동기 셀 편집 검증 블로그 참고: https://blog.ag-grid.com/ag-grid-validation-async/

**우리 케이스 적용**:
- 마스터 행: 작업순번(daily_seq) / 작업일시 / 작업자 / 검증상태(파생 열) / 철거계기번호 / 신설계기번호
- 펼치면 디테일 패널: 검침값 4개(주간/야간/최대전력/무효전력) + 사진 썸네일 + OCR 대조값 + 판정 버튼
- `cellClassRules`로 규칙 위반 셀에 즉시 빨간 테두리/배경 표시 (계기번호 자릿수 오류, 검침값 자릿수 초과 등)
- 검증 상태 열은 서버에서 내려오는 파생 값으로, OCR 결과가 업데이트될 때마다 리프레시

**주의**: AG Grid Master Detail은 ServerSideRowModel과 함께 쓸 경우 일부 제약이 있다. 클라이언트사이드 모델로 시작하는 것이 더 단순하다. (출처: https://github.com/ag-grid/ag-grid/issues)

### 1.2 Airtable — 스프레드시트 느낌의 데이터 원본 보기

**제품**: Airtable
**출처**: https://community.airtable.com/t5/field-validation/td-p/...

Airtable은 스프레드시트처럼 데이터 원본을 보면서 필터·정렬·그룹핑이 가능한 구조다. 단, 필드 유효성 검사(field validation)는 공식 기능으로 지원되지 않으며 수식 열(formula field)로 우회한다. 이는 **Airtable의 가장 큰 약점**으로 커뮤니티에서 반복적으로 지적된다.

우리 포털에 Airtable에서 가져올 것:
- "필터 뷰(Filter View)" 개념: "전체 보기"와 "문제건만 보기"를 클릭 하나로 전환하는 패턴
- 열 고정(freeze), 열 너비 조정, 행 색상 강조 등 엑셀 익숙한 사용자에게 친숙한 UX

Airtable에서 가져오지 말 것:
- 인라인 편집이 즉시 외부 DB에 반영되는 패턴: 우리 케이스에서 awms(한전)는 자동 수정이 불가능하고(plan.md §4), 종로 DB 수정도 신중한 확인 후 apply 흐름으로 설계됨.

### 1.3 Google Sheets 데이터 검증 + 조건부 서식

**제품**: Google Sheets Data Validation
**출처**: Google Sheets 공식 문서 (https://support.google.com/docs/answer/186103)

Google Sheets의 "셀 범위에 규칙 적용 → 위반 시 경고/거부" 패턴은 UX적으로 현장 데이터 원본 보기에 가장 익숙한 참조점이다. 실제로 영준님의 요구("엑셀처럼 데이터 원본 리스트")가 이 경험을 기준으로 한 것이다.

조건부 서식(Conditional Formatting)을 통한 시각화: 오류 셀 빨간색, 주의 노란색, 정상 기본색. 이 세 단계 색상 코딩은 우리 포털에서도 그대로 활용 가능하다.

### 1.4 Handsontable — 순수 스프레드시트 그리드

**제품**: Handsontable
**출처**: https://handsontable.com/

Handsontable은 평면 스프레드시트에 가장 가까운 웹 그리드다. 셀 단위 유효성 검사, 드롭다운, 날짜 피커 등을 내장하지만, **마스터-디테일 구조를 기본 지원하지 않는다**. 우리 데이터 단위(daily_seq)가 사진·검침값·계기번호를 묶은 중첩 구조이므로 Handsontable은 이 케이스에 적합하지 않다.

## 2. 오류/예외만 필터링해 검토하는 워크플로우

### 2.1 예외 기반 검토(Exception-Based Review) — 제조업 MES 패턴

**출처**: https://sgsystemsglobal.com/exception-based-process-review/

제조실행시스템(MES)의 "예외 기반 프로세스 검토(Exception-Based Process Review, EBPR)"는 가장 성숙한 형태의 문제건 집중 검토 패턴이다. 핵심 원리:

1. **모든 레코드를 사람이 보는 것은 낭비**다. 사전 정의된 한도(limit), 추세(trend), 무결성 규칙을 벗어난 것만 사람에게 넘긴다.
2. 이상 없는 것은 시스템이 자동 승인(auto-release). 사람은 예외건에만 집중.
3. 예외 화면은 문제의 우선순위와 유형을 함께 표시한다.

**의약품 배치 검토(Review by Exception) 사례** (출처: https://www.linkedin.com/pulse/review-exception-how-mes-transforms-pharmaceutical-batch/):
제약 MES에서는 전자배치기록(eBR)에 수천 개의 측정값이 들어온다. 모든 값을 사람이 검토하는 것은 불가능하므로, 범위 이탈(out-of-spec)만 하이라이트해 리뷰어에게 제시한다. 합격 항목은 "자동 통과" 표시만 남긴다.

**우리 케이스 적용**:
- "자동통과(auto)" 건은 목록에 보이되 흐리게(문제건과 구분), 기본 뷰는 "문제건만" 필터
- "확인필요(need_human)" → "확인완료(human)"의 플로우가 EBPR의 예외→검토→승인 플로우와 동일
- 상단 요약 배지: 전체 N건 중 자동통과 M건 / 확인필요 K건 → 사람이 볼 것은 K건임을 즉시 파악

### 2.2 Microsoft Purview 데이터 품질 오류 레코드

**출처**: https://learn.microsoft.com/en-us/purview/data-quality-error-records

Microsoft Purview Unified Catalog의 "Data Quality Error Records" 기능은 규칙 위반 레코드를 별도 저장소(Azure Fabric Lakehouse)에 격리하고, UI에서 규칙별 오류 건수와 샘플 레코드를 보여준다. 우리 포털의 "문제건만 필터"에 해당하는 엔터프라이즈 구현 사례다.

**구조적 시사점**: 오류 레코드는 원본과 분리된 뷰이지 별도 테이블이 아니다. 원본 데이터에 "오류 여부" 플래그가 붙은 채 저장되고, UI에서 필터로 솎아내는 구조.

### 2.3 Retool 검증 + 상태 표시기 패턴

**출처**: https://community.retool.com/t/data-validation-for-table-inline-editing/

Retool의 editable table에서 inline editing 시 JS query로 입력값을 검증하고 오류 시 편집을 차단하는 패턴이 실제 내부 도구에서 많이 쓰인다. 상태(status) 열에 Boolean 값 기반 색상 배지를 붙이는 패턴(https://community.retool.com/t/status-indicator-not-displaying-correct-information/)도 참고할 수 있다.

## 3. 실시간/상시(on-write) 정합성 검사 아키텍처

### 3.1 실시간 vs 배치의 올바른 구분

**중요**: Great Expectations, dbt tests, Monte Carlo는 **배치/스케줄 기반** 도구다. 이들을 "실시간 검증 도구"라고 부르는 것은 오해다.

| 도구 | 실제 실행 방식 | 역할 |
|---|---|---|
| dbt tests | 파이프라인 실행 시 트리거, 또는 스케줄 | 규칙 정의 + 파이프라인 내 검증 |
| Great Expectations | Checkpoint 실행 시 (배치) | 기대치(Expectation) 정의 + 배치 검증 |
| Monte Carlo | 데이터 파이프라인 이후 이상치 탐지 + 알림 | 옵저버빌리티(모니터링/경보) |
| DB 트리거 / 앱 서버 on-write | 레코드 쓰기 즉시 | 진짜 실시간 검증 |

출처: https://medium.com/dbt-tests-vs-data-observability
출처: https://montecarlo.ai/getting-started-with-monte-carlo

우리가 원하는 "즉시 검증"은 dbt/GE가 아니라 **앱 서버 on-write 규칙**이다.

### 3.2 on-write 규칙 검증 — 폼 검증 패턴 (UX 관점)

**출처**: https://www.smashingmagazine.com/2022/09/inline-validation-web-forms-ux/

웹 폼의 라이브 인라인 유효성 검사 연구에 따르면:
- 사용자가 포커스를 떠난 후(blur) 검증하는 것이 타이핑 중 즉시 검증보다 UX가 낫다.
- 우리 케이스는 입력 폼이 아니라 "DB에서 이미 들어온 데이터를 보는" 화면이므로, 폼 UX 원칙을 직접 적용하는 것은 맞지 않는다.
- 해당 원칙은 **"데이터가 DB에 들어오는 순간" on-write 서버 측 검증**에 적용된다.

출처: https://blog.logrocket.com/ux-form-validation-inline-or-after-submission/

### 3.3 우리 케이스의 on-write 아키텍처 설계

현재 시스템에서 데이터는 종로맵(작업자 입력) → Firebase RTDB ami-jongno/workStatus/jongno 순으로 흐른다. "상시 검증"을 구현하는 두 가지 경로:

**경로 A — Firebase RTDB Cloud Functions 트리거**:
- 레코드가 쓰일 때(`onWrite`) Cloud Function이 즉시 실행, 가벼운 규칙 검증 후 `validation_flags` 필드를 갱신
- 장점: 완전히 자동, 실시간
- 단점: Cloud Function 비용, 맥 로컬 OCR과의 통합 불가

**경로 B — 포털 조회 시 계산(read-time rules)**: 
- 검증 포털이 데이터를 불러올 때 서버(FastAPI)에서 규칙 검증을 즉시 실행해 `validation_flags`를 붙여 내려줌
- 장점: 맥 로컬 환경에 완벽 통합, 추가 비용 없음, OCR 파이프라인과 동일 프로세스
- 단점: 포털 조회 시에만 검증됨 (데이터가 들어오는 즉시는 아님)
- **plan.md v1 맥 로컬 기준으로는 경로 B가 현실적**

**경로 B 구현 방향**:
1. FastAPI `/results` 엔드포인트가 데이터를 Firebase에서 조회
2. 각 레코드에 대해 가벼운 규칙 즉시 실행(Python, 수 ms)
3. 무거운 OCR 결과는 이미 CSV/DB에 저장된 것 참조
4. 두 결과를 합쳐 `validation_flags` 딕셔너리로 응답에 포함
5. 프론트엔드는 이 플래그를 셀 배경색·뱃지로 시각화

### 3.4 가벼운 규칙 검증 목록 (즉시 실행 가능)

plan.md §6a "정합성 체크" 항목을 코드화:

| 규칙 | 대상 필드 | 즉시 가능 여부 |
|---|---|---|
| 계기번호 11자리 | old_meter_id, new_meter_id | 즉시 |
| 계기번호 타입 자리(3~4번째) 유효값 | old_meter_id, new_meter_id | 즉시 |
| 단상 계기인데 주간/야간 외 검침값 있음 | removal_values + 계기타입 | 즉시 (siteData 조인 필요) |
| 삼상 계기인데 검침값 2개뿐 | removal_values + 계기타입 | 즉시 |
| 최대전력 자릿수 7(소수 포함) 초과 | dm_mt_day | 즉시 |

| 검침값 빈값(필수 필드 누락) | removal_values | 즉시 |
| daily_seq 연번 구멍(누락 감지) | daily_seq | 즉시(정렬 후) |

## 4. 데이터 원본 보기 + 검증이 하나로 통합된 실제 도구 사례

### 4.1 필드 현장 검사 소프트웨어 — Fulcrum

**출처**: https://www.fulcrumapp.com/field-inspection-management/

Fulcrum은 현장 작업자가 모바일로 데이터를 입력하고, 관리자는 웹 포털에서 "모든 제출 레코드를 원본 그대로 보면서 문제건에 검토 태그"를 붙이는 구조다. 계기 교체 현장과 구조가 유사하다.

**Fulcrum의 핵심 패턴**:
- 폼 필드에 **유효성 규칙을 미리 정의** → 현장에서 입력 즉시 오류 차단
- 관리자 포털: "검토 필요" 필터 → 해당 레코드만 보기 → 사진과 함께 원본 검토 → 승인/반려 처리
- "단일 진실 소스(single source of truth)": 사진·좌표·입력값이 하나의 레코드에 묶임

**우리 케이스와 차이**: Fulcrum은 데이터가 **모바일 입력 단계에서** 유효성 검사를 받는다. 우리는 이미 들어온 데이터를 **사후 검증**하는 구조. 하지만 관리자 포털의 UX 구조(원본 리스트 + 문제건 필터 + 사진+값 함께 보기)는 동일하다.

### 4.2 MUI X Data Grid — 마스터-디테일 상태 표시

**출처**: https://mui.com/x/react-data-grid/master-detail/

Material UI(MUI)의 Data Grid 역시 마스터-디테일 패널을 공식 지원한다. 마스터 행에 상태 배지(색상 칩)를 붙이고, 펼치면 상세 폼/뷰가 나오는 패턴. AG Grid보다 구현 진입 장벽이 낮고 React 친화적이다.

"Master-detail is a design pattern for organizing information in which the 'master' area lists the data and the 'detail' sections provide further information." — MUI X 공식 문서

### 4.3 회계/감사 대조 검토 도구 — 계정 조정(Account Reconciliation) 패턴

**출처**: https://ramp.com/blog/account-reconciliation-software

회계 조정(reconciliation) 소프트웨어의 핵심 워크플로우:
1. 두 소스(장부 A vs 장부 B)를 자동 매칭
2. **불일치 건만** 리뷰어에게 제시
3. 리뷰어는 이유를 기록하고 승인/수정

우리 케이스의 정확한 유사체: 작업자 입력값(장부 A) vs OCR 추출값(장부 B)를 자동 대조 → 불일치건 need_human → 사람 판정 → 이력 기록. Wolters Kluwer 같은 회계 감사 도구는 이 패턴의 성숙한 구현체다. (출처: https://www.wolterskluwer.com/en/solutions/cch-tagetik/account-reconciliation)

**핵심 UX 원칙 (회계 도구에서)**: 감사자는 "불일치 항목의 이유(원인 코드)"를 기록한다. 우리의 판정 입력(human / human_skip + 사유)이 이와 동일.

### 4.4 iFormBuilder / Zerion — 필드 워크오더 검증

**출처**: https://zerionsoftware.com

현장 작업 지시(work order) 관리 소프트웨어. 작업 후 데이터가 들어오면 관리 포털에서 사진·측정값을 검토하고 QA 패스/실패를 기록. 우리 케이스(계기 교체 현장 → 포털 검증)와 가장 가까운 업종 유사체다.

## 5. 무겁고(OCR·AI) vs 가벼운(규칙) 검증의 분리

### 5.1 두 트랙의 근본적 차이

| 구분 | 가벼운 규칙 검증 | 무거운 OCR/AI 검증 |
|---|---|---|
| 실행 시간 | 수 ms ~ 수십 ms | 수 초 ~ 수십 초/건 |
| 비용 | CPU 거의 0 | CPU/GPU 집약적, 맥 전용 모델 |
| 신뢰도 | 확정적(규칙이 맞으면 항상 맞음) | 확률적(OCR 오독 가능) |
| 실행 경로 | on-read 또는 on-write, 즉시 | 비동기 잡, 완료 후 결과 저장 |
| 예시 | 계기번호 11자리, 단상/삼상 일치, 자릿수 | PARSeq 검침값 판독, Apple Vision 계기번호 |

### 5.2 분리 아키텍처 — 두 단계 파이프라인

현재 daily_cycle.py는 이 두 트랙을 하나의 배치 스크립트에서 순차로 실행한다. 재설계 방향:

```
[데이터 수신 (Firebase RTDB write)]
          |
          v
[트랙 1: 즉시 규칙 검증]  ← FastAPI /results 조회 시, 또는 Cloud Function
  - 계기번호 형식, 자릿수, 타입 자리
  - 단상/삼상 검침칸 매칭
  - 필수값 빈값
  - daily_seq 연번 구멍
  → validation_flags 즉시 붙임
          |
          v
[트랙 2: 비동기 OCR/AI 검증]  ← daily_cycle.py (배치 또는 수동 실행)
  - PARSeq 검침값 LCD 판독
  - Apple Vision 계기번호 명판
  - 2차 Google Vision
  → daily_state.csv, daily_meterid.csv 에 결과 저장
          |
          v
[포털 화면: 두 결과 합산 표시]
  - 검증 상태 열: 규칙위반 / OCR불일치 / 자동통과 / 확인필요 / 확인완료
  - 셀 배경색: 규칙위반(빨강), OCR주의(노랑), 정상(기본)
```

### 5.3 UX 표면화 — 파생 상태 열(Derived Status Column)

두 트랙의 결과를 사용자에게 표시하는 핵심 장치는 **파생 상태 열**이다. 이 열에 들어오는 값의 우선순위:

```
(1) 규칙 위반 있음 → "형식오류" (빨강, 즉시)
(2) need_human → "확인필요" (주황, OCR 비동기 결과)
(3) human / human_skip → "확인완료" (초록, 사람 판정)
(4) auto / pass2 / google → "자동통과" (회색, 흐리게)
(5) 아직 OCR 미실행 → "검증대기" (파랑, 배치 미실행)
```

이 열 하나만 봐도 사용자가 어떤 행에 주의를 기울여야 하는지 즉시 파악 가능하다.

### 5.4 제품 유사 사례 — Cupcake Design System (AG Grid 검증 패턴)

**출처**: https://cupcake-design-system.github.io/ag-grid/validations/

셀 단위 검증(At cell level)과 테이블 전체 검증(At table level)을 분리하는 AG Grid 기반 구현 패턴. 셀 완료 즉시 인라인 표시, 제출 시 전체 검증 표시. 우리의 "규칙 즉시 + OCR 배치" 이중 레이어와 구조적으로 동일.

### 5.5 OCR/AI 파이프라인 비동기 처리 패턴

**출처**: https://towardsdatascience.com/scalable-ocr-pipelines-using-aws/

OCR 파이프라인의 성숙한 아키텍처는 동기 요청-응답이 아니라 **잡 큐(job queue) 패턴**이다:

1. 데이터 수신 → 큐에 잡 추가
2. 워커(맥 OCR 프로세스)가 큐에서 잡 꺼내 처리
3. 결과를 DB/CSV에 기록
4. 포털은 결과가 준비된 것과 아직 대기 중인 것을 구분 표시

현재 daily_cycle.py가 이 역할을 하고 있으나, 포털에서 "아직 OCR 미실행(검증대기)" 상태를 별도 표시하지 않아 배치 실행 전과 후의 화면 차이가 불분명하다. 이 상태를 명시적으로 표시하면 "배치를 돌렸나?" 불확실성이 사라진다.

### 5.6 dbt + Great Expectations: 규칙 정의 레이어로서의 역할

**출처**: https://medium.com/dbt-tests-vs-data-observability (dbt 규칙 vs 옵저버빌리티)
**출처**: https://pipecode.ai/blog/dbt-tests-vs-great-expectations-vs-soda-core

dbt tests와 Great Expectations는 "배치 실행" 도구지만, **규칙을 코드로 명시적으로 정의하는 방식**은 우리의 규칙 검증 모듈에 그대로 적용 가능하다. 예) GE의 `expect_column_value_lengths_to_equal(11)` 스타일로 Python에서 규칙을 선언적으로 정의하면 유지보수가 쉬워진다.

현재 daily_cycle.py에 분산된 검증 로직을 별도 `validation_rules.py`로 모듈화하고, 이 파일이 FastAPI의 on-read 즉시 검증과 배치 OCR 후처리 모두에서 import되면 규칙 단일 관리가 가능하다.

## 6. 우리 케이스 특수 고려사항 (plan.md 연계)

### 6.1 awms 자동 수정 불가 — 검증의 진짜 가치는 예방과 목록

plan.md §4에 명시: awms(한전)는 자동 수정 불가(OTP 구조). 따라서 인라인 편집이 즉시 외부 DB를 고치는 Airtable/Google Sheets 패턴은 우리에게 적용되지 않는다.

검증 포털의 핵심 산출물:
- "수정 필요 리스트" (awms에서 수동으로 고쳐야 할 항목)
- "이력 기록" (무엇을 왜 어떻게 판정했는지)
- 종로 DB에 대한 반영(/apply)만 자동화 가능

이 제약은 UX 설계에서 **"수정 버튼"보다 "판정 버튼"을 강조**해야 함을 의미한다.

### 6.2 단일 사용자, 로컬 맥, 데스크톱

plan.md §5: v1은 영준님 맥 로컬, v2는 맥미니 전용기. 협업/멀티플레이어 기능 불필요. 따라서 엔터프라이즈 데이터 옵저버빌리티 도구(Monte Carlo 월 수만 달러)의 클라우드 인프라는 과도하다. 패턴과 UX만 참조하고 직접 채택 X.

### 6.3 plan.md의 현재 설계와 이 조사의 관계

plan.md §3의 "[검증 실행]" 버튼은 현재 배치 흐름의 진입점이다. 이 조사는 그 흐름을 전면 폐기하는 것이 아니라 **진화**를 제안한다:

| 현재 | 재설계 방향 |
|---|---|
| [검증 실행] 1회 → 전체 배치 | OCR 배치는 유지, 규칙 검증은 조회 시 즉시 |
| 결과 CSV를 보는 검증 탭 | 원본 데이터 그리드가 검증 상태 열 포함 |
| 배치 후 "문제건만" 필터 | 규칙 위반은 즉시 표시, OCR 결과는 배치 후 갱신 |
| 검증 모달 = 사진+대조 | 동일, 단 규칙 위반과 OCR 불일치를 구분 표시 |

## 핵심 시사점 요약 (7개)

### 시사점 1 — 검증 상태 열이 그리드와 검증을 하나로 합친다

원본 데이터 그리드에 "파생 검증 상태 열"을 붙이면, 화면이 데이터 브라우저이자 검증 도구가 된다. 사용자는 별도 "검증 탭"으로 이동할 필요 없이 원본 목록에서 바로 문제를 파악한다. AG Grid의 `cellClassRules`와 MUI X Data Grid의 마스터-디테일 패턴이 이를 구현하는 가장 직접적인 기술 수단이다.

### 시사점 2 — 가벼운 규칙 검증은 조회 시 즉시, OCR은 배치 후 갱신

두 트랙을 명확히 분리해야 한다. 계기번호 형식·자릿수·단상삼상 일치·검침값 빈값 등 계산 비용이 거의 0인 규칙은 FastAPI `/results` 조회 시 즉시 실행해 `validation_flags`를 붙인다. PARSeq/Apple Vision OCR은 배치(daily_cycle.py)가 끝난 뒤 결과가 CSV에 저장되면 포털이 이를 참조한다. 두 트랙의 결과가 모두 같은 "검증 상태 열"에 표면화되므로 사용자는 이 분리를 의식하지 않아도 된다.

### 시사점 3 — 예외 기반 검토(EBPR) 패턴이 "문제건만" 필터의 이론적 근거

제조업 MES의 예외 기반 프로세스 검토와 제약 배치기록 시스템(Review by Exception)은 이미 수십 년간 "전건 검토는 낭비, 예외건만 사람이 본다"는 원칙을 검증했다. 자동통과 건을 흐리게 표시하고, 기본 뷰를 "문제건만"으로 설정하고, 상단 요약 배지(전체 N / 확인필요 K)를 두는 것은 이 패턴의 직접 적용이다.

### 시사점 4 — awms 수정 불가 제약이 UX 언어를 결정한다

Airtable·Google Sheets식 "인라인 편집 즉시 저장"은 awms에 적용할 수 없다. 대신 검증 포털의 핵심 행동은 "판정(verdict)"이다. 회계 감사 도구의 "불일치 이유 기록 + 승인/반려" 워크플로우가 더 적합한 참조 모델이다. UX에서 "수정" 버튼보다 "확인완료 / 확인불가" 버튼을 강조해야 한다.

### 시사점 5 — "검증대기" 상태를 명시적으로 표시해야 배치 불확실성이 사라진다

OCR 배치를 아직 돌리지 않은 건과 이미 자동통과한 건이 화면에서 구분되지 않으면 "검증이 됐나 안 됐나"를 사용자가 알 수 없다. "검증대기(OCR 미실행)" 상태를 별도 색상(파랑)으로 명시하면 [검증 실행] 버튼을 눌러야 할 시점이 명확해진다.

### 시사점 6 — 규칙을 선언적으로 코드화(validation_rules.py)하면 유지보수가 쉬워진다

dbt tests / Great Expectations의 진짜 기여는 "배치 실행" 능력이 아니라 **규칙을 코드로 명시적으로 정의하는 문화**다. 현재 daily_cycle.py에 분산된 검증 로직을 `validation_rules.py`로 분리해, FastAPI on-read 즉시 검증과 배치 OCR 후처리 양쪽에서 import하면 규칙 변경이 한 곳에서 전파된다. 새 규칙 추가(예: 최대↔무효 뒤바뀜 탐지)를 이 파일에만 추가하면 된다.

### 시사점 7 — 마스터-디테일이 flat 스프레드시트보다 우리 데이터 구조에 맞다

daily_seq 하나에 철거계기번호 + 신설계기번호 + 검침값 4개 + 사진 여러 장이 묶인 중첩 구조는 Handsontable 같은 평면 그리드에 억지로 펼치면 열이 수십 개가 되고 사진은 표시 불가능하다. AG Grid 또는 MUI X의 마스터-디테일 패턴이 이 구조를 자연스럽게 표현한다. 마스터 행에 핵심 식별 정보(작업순번·일시·작업자·검증상태·계기번호)만 두고, 펼침 패널에 검침값과 사진을 넣으면 "엑셀처럼 보이되 사진까지 볼 수 있는" 화면이 가능하다.
