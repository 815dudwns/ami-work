## 핵심 규칙 (사고 이력 기반)

- **★작업 전 판별 절차 — 세션 시작 시 `git log --oneline main..HEAD` / `main...HEAD`로 main과의 차이부터 확인하고, 고칠 파일이 실제로 폰에 로드되는 경로인지 grep으로 먼저 증명하라.** 발주서가 지목한 폴더를 그대로 믿지 말 것. 최소 3가지를 대조한다: ①`cst-app/android/app/build.gradle`의 `versionName`이 `cst-input/cst-version.json`과 일치하는가(=네이티브가 배포본) ②`grep -rn "github.io\|loadUrl" cst-app/android/app/src/main/java`로 그 화면이 원격 로드되는가 ③`unzip -l cst-input/amiqueue.apk | grep assets/public`에 그 파일이 실제로 들어있는가. 어긋나면 **손대기 전에 PM 보고**.
  - 사고 2026-08-11: 같은 기능을 **두 번 헛짚었다** — 1차 `ami-queue-www/collect.js`(죽은 옛 웹뷰, revert), 2차 `cst-input/www/collect.js`(이것도 죽음). 실체는 네이티브 `cst-app/.../ui/CollectScreen.kt`였다. 두 번 다 이 카드에 경고가 적혀 있었는데, **워크트리가 main보다 54커밋 뒤처져 낡은 사본을 읽어서** 못 봤다. 그래서 판별 절차보다 **main 동기화 확인이 먼저**다.
- **awms 팀 경계 = MOBCST(`mob/cst`)**. 계기팀 MOBMTR(`mob/mtr`)와 교차호출 시 405. 통신팀은 MOBCST만.
- **★아미큐 화면은 전부 네이티브(cst-app, Kotlin Compose)** — 계기번호/QR뿐 아니라 **수집·설정·사전설정 등 모든 UI**가 네이티브다. 수집·QR=`ui/CollectScreen.kt`, 설정·공사설정(작업자2/공사번호)=`ui/SettingsScreen.kt`. UI 수정은 APK 재빌드 필요(assembleDebug, debug.keystore).
  - **`ami-queue-www/`는 죽은 옛 웹뷰 버전**(APP_VER v0614f, 2026-06 이전 동결). 네이티브가 로드하지 않으므로 **여기 고치면 폰 반영 0**. cst-app 소스의 유일한 원격 로드는 `AwmsLoginScreen.kt:29` awms-bridge-inject.js 하나뿐.
  - 판별법: 손대기 전 `grep -rn "github.io" cst-app/.../java`로 그 화면이 원격 로드되는지 먼저 확인. 애매하면 PM에 확인.
  - **폰 UI를 건드리기 전에, 백엔드(`cst-input/backend/app.py`)에서 awms 원시응답을 덤프해 맥에서 실측할 수 있는지 먼저 보라.** 대부분의 필드명 확정·진단은 APK 재빌드 없이 백엔드에서 끝난다(2026-07-27 저장값 진단 건 실사례).
- **모뎀맥 바코드 = Code 93** — ML Kit FORMAT_CODE_93 누락 시 못 읽음. 통신방식 판별은 모뎀 MAC hex 규칙(E0AEED=ksplc/44B433=hpgp 등).
- **아미맵 DB = ami-work-1c49a** (종로 ami-jongno 아님). 무료요금제(Spark)라 과금 없음.
- 아미맵 배포 = `js/auth.js` FORCE_LOGOUT_VERSION은 긴급 시만(잦은 범프가 초기화 유발).
- **`cst-input/`에서 살아있는 것 = 백엔드(`backend/app.py`, FastAPI 8766)와 자동업뎃 기준(`cst-version.json`)뿐.** 웹 프론트(collect.js 등)는 네이티브 전환으로 죽었다. 버전만 올리고 APK 미교체 = 무한 업뎃 루프.
- **★backend/app.py 수정 = 커밋만으론 반영 0. `cst-input/restart.sh` 로 재구동하고, 로그 형식으로 반영을 확인하는 데까지가 1건이다.**
  - `--reload`는 **안 쓴다**(2026-08-11 판단): 감시범위가 `ami-work` 전체 `.py` 465개라 다른 팀 저장에 현장 백엔드가 끌려다니고, saveAct는 사진 수 MB를 미는 스트리밍이라 **전송 도중 재시작 = 그 건 유실**이다.
  - `start.sh`는 **기동 전용** — 포트가 응답하면 "이미 실행 중"으로 그냥 끝난다. 고치고 start.sh를 다시 돌려도 **아무 일도 일어나지 않는다.** 재구동은 `restart.sh`.
  - 확인 수단 2개: `restart.sh --check`(= `/api/health`의 `stale`) · `[saveact]` 로그. stale이면 로그에 경고가 붙는다.
  - **재구동 타이밍은 영준님 현장작업과 겹치면 안 된다** — `restart.sh`가 진행 중 전송(status=sending)을 확인해 물어본다. 임의 강행 금지.
  - 사고 2026-08-11: 커밋해 놓고 재구동을 안 해 **12일 된 코드가 계속 돌았다.** 그 프로세스엔 `addl`/`EXT_CONN_DEV` 산출이 아예 없어 폰을 두 번(2.2.8·2.2.9) 고쳐도 변화가 0이었고 반나절을 태웠다. 그 전엔 변대주가 안 올라간 원인도 같은 것이었다.
- **아미큐 반영 경로는 3층이고 서로 별개다** — 네이티브 UI = **APK 재빌드**(assembleDebug) / 백엔드 = **restart.sh** / 자동업뎃 기준 = `cst-version.json`. 하나만 올리고 "반영됐겠지" 금지.
